CKA Lab Tutorial / Overview & How to Use

Hands-On CKA Lab

This tutorial builds a real Kubernetes lab on your Mac, then walks you through every practice case from the CKA study guide. You run real commands, break real things, and fix them. Reading passes the time; doing passes the exam.

Two Environments — Why
Most cases run on KinD (Kubernetes in Docker) — it starts in a minute and needs little memory. But some Cluster-domain tasks touch a node's own operating system: kubeadm setup, etcd backup, cluster upgrade, kubelet, static pods. A KinD "node" is a container, not a machine, so those tasks want real VMs. You already have multipass for that. This split matches how the real exam clusters behave.

What You Will Build

EnvironmentToolRuns which labs
3-node container clustercolima + kindA–F: workloads, scheduling, networking, storage, troubleshooting, RBAC
2 real Linux VMsmultipassG–I: etcd, cluster upgrade, static pods & API server

The Loop — Follow It for Every Lab

  1. Setup — create the scenario (a deployment, a broken pod, a policy).
  2. Do it — perform the task yourself first, without reading the answer.
  3. Verify — run the check command and compare to the expected output.
  4. Clean up — delete what you made, so the next lab starts clean.
Track Your Progress
Each step has a checkbox. Tick it as you finish. Your marks are saved in this browser, so you can close the page and come back. The sidebar shows how many steps you have done per section.
Before You Start
Budget about 6 GB RAM for the KinD cluster and another 4 GB if you run the VMs at the same time. Close heavy apps. You can also do the KinD labs first, tear them down, then do the VM labs.

Prerequisites & Install KinD

You already have kubectl, helm, and multipass. You still need a container engine and kind. On Apple Silicon, colima is the simplest free engine.

Install colima and kind

bash# Install the container engine and kind (kubectl + helm already present)
brew install colima kind

# Start colima with enough room for a 3-node cluster
colima start --cpu 4 --memory 6 --disk 40

# Confirm the Docker engine is up and kind can see it
docker info | grep -i "server version"
kind version
Verify
docker info prints a Server Version with no error. kind version prints v0.33.0 or newer. If docker says "cannot connect", colima is not started — run colima start.
What colima Does
colima runs a small Linux VM and a Docker engine inside it. kind then creates Kubernetes "nodes" as Docker containers in that engine. So the chain is: colima (Linux VM) → Docker → kind node containers → Kubernetes. When you stop colima, the whole lab pauses; start it again and the cluster returns.
If You Use Docker Desktop Instead
Docker Desktop also works. Start it, skip colima, and give it 6 GB in Settings → Resources. Everything else in this tutorial is identical.

Create the KinD Cluster KinD

You build a 3-node cluster (1 control plane + 2 workers). You turn off the default network plugin so you can install Calico — the default plugin does not enforce NetworkPolicy, and you need that for the networking lab.

Write the cluster config

Save this as kind-config.yaml:

yamlkind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  disableDefaultCNI: true       # turn off kindnet, so Calico can enforce NetworkPolicy
  podSubnet: "192.168.0.0/16"   # matches Calico's default range
nodes:
- role: control-plane
  kubeadmConfigPatches:
  - |
    kind: InitConfiguration
    nodeRegistration:
      kubeletExtraArgs:
        node-labels: "ingress-ready=true"   # lets ingress-nginx schedule here
  extraPortMappings:              # expose 80/443 on your Mac for Ingress
  - containerPort: 80
    hostPort: 80
    protocol: TCP
  - containerPort: 443
    hostPort: 443
    protocol: TCP
- role: worker
- role: worker

Create the cluster

bashkind create cluster --name cka --config kind-config.yaml

# kubectl is pointed at the new cluster automatically
kubectl config current-context     # kind-cka
kubectl get nodes
Nodes Show NotReady — That Is Expected
You disabled the default CNI, so nodes stay NotReady until you install Calico on the next page. Do not panic — this is by design.
Verify
kubectl get nodes lists three nodes: cka-control-plane, cka-worker, cka-worker2. Status is NotReady for now.
See the Node Containers
Run docker ps. Each Kubernetes node is a Docker container. You will use docker exec into these later to explore etcd and static pods — a trick the real exam does not need, but great for learning.

Install Add-ons KinD

A bare cluster cannot run every lab. Install four add-ons, each for a clear reason. Do Calico first — it makes the nodes Ready.

1 · Calico — network + NetworkPolicy

Calico gives pods a network and, unlike the default plugin, enforces NetworkPolicy. The networking lab needs this.

bashkubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.1/manifests/calico.yaml

# Wait until Calico is running, then nodes turn Ready
kubectl -n kube-system rollout status ds/calico-node --timeout=180s
kubectl get nodes
Verify
All three nodes now show Ready. kubectl get pods -n kube-system | grep calico shows calico-node pods Running.

2 · metrics-server — for HPA, QoS, and kubectl top

metrics-server collects CPU/memory usage. Without it, HPA shows <unknown> and kubectl top fails. On kind you must add one flag, because kind's kubelet uses a self-signed certificate.

bashkubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# kind fix: trust the kubelet's self-signed cert
kubectl -n kube-system patch deployment metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

kubectl -n kube-system rollout status deploy/metrics-server --timeout=120s
Verify
After about a minute, kubectl top nodes prints CPU and memory numbers instead of an error.

3 · ingress-nginx — for the Ingress lab

bashkubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/kind/deploy.yaml

kubectl -n ingress-nginx rollout status deploy/ingress-nginx-controller --timeout=180s
Verify
kubectl get pods -n ingress-nginx shows the controller Running. Because of the port mappings, an Ingress on host localhost will answer on your Mac.

4 · Gateway API CRDs — for the Gateway lab (optional)

The Gateway API objects are CustomResourceDefinitions. Install the standard set. This alone satisfies the "install the CRDs a Gateway needs" case.

bashkubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.1/standard-install.yaml

kubectl get crd | grep gateway.networking.k8s.io
Controller Optional
CRDs let you create Gateway and HTTPRoute objects and see them accepted. To actually route traffic you also need a controller (for example nginx-gateway-fabric via Helm). That is heavier; the CRD step is enough to practice the exam task.
Storage Is Already Here
kind ships a default StorageClass named standard. Run kubectl get sc — you use it in the storage lab. No install needed.

Lab A · Workloads KinD

Deployments, rolling updates, sidecars, health probes, and autoscaling. Create a scratch namespace first, then work inside it.

bashkubectl create namespace lab
kubectl config set-context --current --namespace=lab

A1 · Create, scale, and roll back a Deployment

Task: Run web (nginx:1.25, 3 replicas). Update to 1.26. Then roll back.

bashkubectl create deployment web --image=nginx:1.25 --replicas=3
kubectl set image deployment/web nginx=nginx:1.26
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout undo deployment/web
Verify
kubectl describe deploy web | grep Image shows nginx:1.25 again after the undo.

A2 · Add a native sidecar

Task: Run a pod where a sidecar starts before the app and keeps running.

bashcat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-demo
spec:
  initContainers:
  - name: shipper
    image: busybox
    restartPolicy: Always            # this makes it a native sidecar
    command: ["sh","-c","while true; do echo shipping logs; sleep 5; done"]
  containers:
  - name: app
    image: nginx
EOF
kubectl get pod sidecar-demo
Verify
kubectl get pod sidecar-demo shows 2/2 Ready. kubectl logs sidecar-demo -c shipper streams "shipping logs".

A3 · Add liveness and readiness probes

Task: Give an app a readiness probe (controls traffic) and a liveness probe (restarts it). Then watch each behave differently.

bashcat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: probes
  labels: { app: probes }
spec:
  containers:
  - name: app
    image: registry.k8s.io/e2e-test-images/agnhost:2.47
    args: ["netexec","--http-port=8080"]
    readinessProbe:
      httpGet: { path: /readyz, port: 8080 }
      periodSeconds: 3
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 3
      failureThreshold: 2
EOF
kubectl expose pod probes --port=8080
kubectl get endpoints probes

Now break readiness (the agnhost app lets you flip its own health):

bash# Force /readyz to fail — pod leaves Endpoints but is NOT restarted
kubectl exec probes -- /bin/sh -c "curl -s localhost:8080/readyz?state=false" 2>/dev/null || true
kubectl get endpoints probes     # the pod IP disappears
kubectl get pod probes           # RESTARTS stays 0
The Point
Readiness removed the pod from the Service (no traffic) but left it running. A liveness failure, by contrast, restarts the container — watch the RESTARTS column climb if /healthz fails. This is the difference the exam tests.
Verify
After breaking readiness, kubectl get endpoints probes shows no addresses, yet kubectl get pod probes still shows the pod Running with 0 restarts.

A4 · Autoscale on CPU (HPA)

Task: Add an HPA to a deployment (min 1, max 5, 50% CPU), then drive load and watch it scale.

bashkubectl create deployment php --image=registry.k8s.io/hpa-example
kubectl set resources deployment php --requests=cpu=100m --limits=cpu=200m
kubectl expose deployment php --port=80
kubectl autoscale deployment php --cpu-percent=50 --min=1 --max=5

# Generate load from a throwaway pod (leave it running, watch another terminal)
kubectl run -it load --image=busybox --restart=Never --rm -- \
  /bin/sh -c "while true; do wget -q -O- http://php; done"
bash# In a second terminal:
kubectl get hpa php --watch
Verify
The HPA TARGETS climbs above 50% and REPLICAS grows toward 5. Stop the load pod (Ctrl-C) and replicas fall back after a few minutes.

Clean up Lab A

bashkubectl delete deploy web php --ignore-not-found
kubectl delete pod sidecar-demo probes --ignore-not-found
kubectl delete svc probes php --ignore-not-found
kubectl delete hpa php --ignore-not-found

Lab B · Scheduling & Resource Control KinD

Steer where pods run and how resources are shared: affinity, taints, priority/preemption, QoS, quotas, and disruption budgets. Stay in the lab namespace.

B1 · Node affinity — pin to a labelled node

bash# Label one worker as SSD
kubectl label node cka-worker disktype=ssd

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: ssd-pod }
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - { key: disktype, operator: In, values: [ssd] }
  containers:
  - { name: app, image: nginx }
EOF
kubectl get pod ssd-pod -o wide
Verify
kubectl get pod ssd-pod -o wide shows it scheduled on cka-worker (the SSD node), never cka-worker2.

B2 · Taints and tolerations

bash# Repel pods from worker2
kubectl taint node cka-worker2 tier=critical:NoSchedule

# A pod without the toleration will avoid worker2; add one to allow it
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: tolerant }
spec:
  tolerations:
  - { key: tier, operator: Equal, value: critical, effect: NoSchedule }
  nodeName: cka-worker2
  containers:
  - { name: app, image: nginx }
EOF
kubectl get pod tolerant -o wide
kubectl taint node cka-worker2 tier=critical:NoSchedule-   # remove the taint
Verify
The tolerant pod runs on cka-worker2. A pod without the toleration stays off it.

B3 · PriorityClass and preemption

Task: Fill one node with low-priority pods, then schedule a high-priority pod that must evict one to fit.

bashkubectl create priorityclass low  --value=1000
kubectl create priorityclass high --value=100000

# Find a worker's allocatable CPU so you can fill it
kubectl describe node cka-worker | grep -A5 Allocatable

# Fill cka-worker with low-priority pods (tune replicas/cpu to exceed allocatable)
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata: { name: filler }
spec:
  replicas: 4
  selector: { matchLabels: { app: filler } }
  template:
    metadata: { labels: { app: filler } }
    spec:
      priorityClassName: low
      nodeSelector: { disktype: ssd }        # pin all to cka-worker
      containers:
      - name: c
        image: nginx
        resources: { requests: { cpu: "500m" } }
EOF
bash# Now a high-priority pod that also needs cka-worker — it preempts a filler
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: vip }
spec:
  priorityClassName: high
  nodeSelector: { disktype: ssd }
  containers:
  - name: c
    image: nginx
    resources: { requests: { cpu: "500m" } }
EOF
kubectl get events | grep -i preempt
kubectl get pods -l app=filler
Verify
vip reaches Running. An event mentions preemption, and one filler pod was evicted to free room. If nothing preempts, raise the filler replicas or CPU requests until the node is truly full.

B4 · QoS classes

bash# Guaranteed: requests == limits
kubectl run g --image=nginx --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"g","image":"nginx","resources":{"requests":{"cpu":"100m","memory":"64Mi"},"limits":{"cpu":"100m","memory":"64Mi"}}}]}}'
# BestEffort: nothing set
kubectl run b --image=nginx --restart=Never

kubectl get pod g -o jsonpath='{.status.qosClass}{"\n"}'   # Guaranteed
kubectl get pod b -o jsonpath='{.status.qosClass}{"\n"}'   # BestEffort
Verify
Pod g reports Guaranteed; pod b reports BestEffort. Under memory pressure the kubelet would evict b first.

B5 · ResourceQuota

bashkubectl create namespace quota-demo
kubectl create quota cpu-quota --hard=requests.cpu=1 -n quota-demo

# First pod (500m) fits; a second 500m pod is rejected at 1 CPU total
kubectl run p1 --image=nginx -n quota-demo --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"p1","image":"nginx","resources":{"requests":{"cpu":"500m"}}}]}}'
kubectl run p2 --image=nginx -n quota-demo --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"p2","image":"nginx","resources":{"requests":{"cpu":"600m"}}}]}}'
kubectl describe quota cpu-quota -n quota-demo
Verify
p2 is rejected with a "exceeded quota" error. kubectl describe quota shows used 500m of 1 CPU. Note: once a quota sets requests.cpu, every pod must declare that request.

B6 · PodDisruptionBudget during a drain

bashkubectl create deployment web --image=nginx --replicas=3
kubectl create pdb web-pdb --selector=app=web --min-available=2

# Find which worker holds web pods, then drain it
kubectl get pods -l app=web -o wide
kubectl drain cka-worker2 --ignore-daemonsets --delete-emptydir-data
kubectl get pdb web-pdb
kubectl uncordon cka-worker2     # bring the node back after
Verify
The drain evicts web pods one at a time and never drops below 2 available. kubectl get pdb shows ALLOWED DISRUPTIONS. If the app had only 2 replicas, the drain would block — that is the PDB protecting you.

Clean up Lab B

bashkubectl delete pod ssd-pod tolerant vip g b --ignore-not-found
kubectl delete deploy filler web --ignore-not-found
kubectl delete pdb web-pdb --ignore-not-found
kubectl delete priorityclass low high --ignore-not-found
kubectl delete ns quota-demo --ignore-not-found
kubectl label node cka-worker disktype-

Lab C · Services & Networking KinD

Services, Endpoints, DNS, NetworkPolicy, and Ingress. NetworkPolicy is enforced because you installed Calico.

C1 · Expose a Deployment and confirm Endpoints

bashkubectl create deployment web --image=nginx --replicas=2
kubectl expose deployment web --port=80
kubectl get endpoints web
Verify
kubectl get endpoints web lists two pod IPs. Test it: kubectl run t --image=busybox --rm -it --restart=Never -- wget -qO- http://web returns the nginx welcome HTML.

C2 · Fix a Service with no Endpoints

Task: Break the Service on purpose (wrong selector), see empty Endpoints, then fix it.

bashkubectl patch svc web -p '{"spec":{"selector":{"app":"wrong"}}}'
kubectl get endpoints web      # now empty — no pods match

# Fix: point the selector back at the real pod label
kubectl patch svc web -p '{"spec":{"selector":{"app":"web"}}}'
kubectl get endpoints web      # IPs return
Verify
Endpoints are empty after the bad patch and repopulate after the fix. This is the single most common Service bug on the exam.

C3 · NetworkPolicy — deny all, then allow only frontend

bashkubectl create namespace netpol
kubectl label ns netpol name=netpol
kubectl -n netpol run backend  --image=nginx --labels=app=backend --port=80
kubectl -n netpol expose pod backend --port=80
kubectl -n netpol run frontend --image=busybox --labels=app=frontend -- sleep 3600
kubectl -n netpol run other    --image=busybox --labels=app=other    -- sleep 3600

# Before any policy: both can reach backend
kubectl -n netpol exec frontend -- wget -qO- --timeout=3 http://backend && echo OK
kubectl -n netpol exec other    -- wget -qO- --timeout=3 http://backend && echo OK
bash# Deny all ingress in the namespace, then allow only app=frontend
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: netpol }
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-frontend, namespace: netpol }
spec:
  podSelector: { matchLabels: { app: backend } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: frontend } }
    ports:
    - { protocol: TCP, port: 80 }
EOF
bash# Now frontend works; other times out
kubectl -n netpol exec frontend -- wget -qO- --timeout=3 http://backend && echo "frontend OK"
kubectl -n netpol exec other    -- wget -qO- --timeout=3 http://backend || echo "other BLOCKED"
Verify
frontend gets the page; other times out and prints BLOCKED. If both still work, Calico did not install correctly — recheck the add-ons page.

C4 · CoreDNS resolution

bashkubectl -n netpol exec frontend -- nslookup backend
kubectl -n netpol exec frontend -- nslookup backend.netpol.svc.cluster.local
Verify
Both lookups return the Service ClusterIP. This proves the FQDN pattern <svc>.<ns>.svc.cluster.local.

C5 · Ingress

bashkubectl create deployment site --image=nginx
kubectl expose deployment site --port=80
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: site }
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend: { service: { name: site, port: { number: 80 } } }
EOF
sleep 5
curl -s http://localhost/ | grep -i "welcome to nginx"
Verify
curl http://localhost/ returns the nginx welcome page — traffic went from your Mac, through the mapped port, to ingress-nginx, to the Service, to a pod.

Clean up Lab C

kubectl delete svc web site --ignore-not-found
kubectl delete ingress site --ignore-not-found
kubectl delete ns netpol --ignore-not-found

Lab D · Storage KinD

The admin/developer contract: a PV offers storage, a PVC claims it, a pod mounts the claim. Then dynamic provisioning with the default StorageClass.

D1 · Static PV + PVC + pod

bashcat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolume
metadata: { name: pv-manual }
spec:
  capacity: { storage: 1Gi }
  accessModes: [ReadWriteOnce]
  storageClassName: manual
  hostPath: { path: /tmp/pv-manual }
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pvc-manual, namespace: lab }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: manual
  resources: { requests: { storage: 1Gi } }
EOF
kubectl get pv,pvc -n lab
bashcat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: uses-pvc, namespace: lab }
spec:
  volumes:
  - name: data
    persistentVolumeClaim: { claimName: pvc-manual }
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - { name: data, mountPath: /data }
EOF
kubectl -n lab exec uses-pvc -- sh -c "echo hello > /data/f && cat /data/f"
Verify
The PVC STATUS is Bound. The pod starts and writes/reads /data/f.

D2 · Dynamic provisioning (default StorageClass)

bashkubectl get sc     # 'standard' is the default on kind
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pvc-dynamic, namespace: lab }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }    # no storageClassName → uses default
EOF
kubectl -n lab get pvc pvc-dynamic
Verify
A PV is created automatically and the PVC becomes Bound with no PV made by hand. That is dynamic provisioning.
Honest Limit — PVC Expansion
The guide's "expand a PVC 2Gi → 5Gi" case needs a StorageClass with allowVolumeExpansion: true and a driver that supports it. kind's default local-path provisioner does not support online expansion, so this one case cannot be fully completed on kind. Practice the concept here (patch the PVC size and read the error), and do the real expansion on a cloud cluster or a CSI driver that supports it. The command to know is: kubectl patch pvc <name> -p '{"spec":{"resources":{"requests":{"storage":"5Gi"}}}}'.

Clean up Lab D

bashkubectl -n lab delete pod uses-pvc --ignore-not-found
kubectl -n lab delete pvc pvc-manual pvc-dynamic --ignore-not-found
kubectl delete pv pv-manual --ignore-not-found

Lab E · Troubleshooting KinD

Break things on purpose and fix them. This is 30% of the exam — practice the reflexes.

E1 · CrashLoopBackOff — find the cause

bash# A container that exits immediately with an error
kubectl run crasher --image=busybox --restart=Always -- /bin/sh -c "echo boom; exit 1"
sleep 15
kubectl get pod crasher                 # CrashLoopBackOff
kubectl describe pod crasher | tail -20 # Events + Last State
kubectl logs crasher --previous         # output of the crashed run
Verify
logs --previous shows "boom". You located the cause without guessing. Fix would be to correct the command.

E2 · Debug a distroless pod with no shell

bashkubectl run distroless --image=gcr.io/distroless/static-debian12 --command -- sleep 3600
# It has no shell, so exec fails. Attach an ephemeral debug container:
kubectl debug distroless -it --image=busybox --target=distroless -- sh -c "ps; ls /proc/1/root"
Verify
A plain kubectl exec distroless -- sh fails (no shell). The kubectl debug busybox container opens and can see the target's processes.

E3 · Broken Service — reuse the C2 skill

Break a Service selector, confirm empty Endpoints, fix it — same drill as Lab C2. On the exam, a "app can't reach app" task is almost always a label/selector mismatch or wrong namespace.

E4 · Simulate a NotReady node and recover

bash# Stop the kubelet inside a worker's container — the node goes NotReady
docker exec cka-worker2 systemctl stop kubelet
sleep 20
kubectl get nodes                       # cka-worker2 = NotReady

# Recover: start the kubelet again
docker exec cka-worker2 systemctl start kubelet
sleep 15
kubectl get nodes                       # back to Ready
Why This Mirrors the Exam
On a real node you would run systemctl status kubelet and journalctl -u kubelet to diagnose, then restart it. Here you drive the kubelet through docker exec because the node is a container — but the fix (restart kubelet) is exactly the same.
Verify
The node flips NotReady → Ready as you stop and start the kubelet.

Clean up Lab E

bashkubectl delete pod crasher distroless --ignore-not-found

Lab F · RBAC KinD

Grant a subject exactly the access it needs, then prove it with auth can-i. Runs fully on KinD.

F1 · Role + RoleBinding for a user

bashkubectl create namespace app
kubectl create role pod-reader --verb=get,list,watch --resource=pods -n app

kubectl auth can-i delete pods --as=dev -n app     # no
kubectl auth can-i list pods   --as=dev -n default # no (namespaced)
Verify
First check prints yes; the other two print no. The Role is additive and namespaced, exactly as designed.

Provision VMs + kubeadm VMs

Build a real 2-node cluster with multipass (already installed). Here you touch the node's operating system, so etcd, upgrades, and static pods behave exactly like the exam.

Resources
Each VM uses ~2 GB RAM. If your KinD cluster is still running, tear it down first (Reference → Teardown) to leave room.
V0 · Start the multipass daemon first
A stopped daemon makes every command fail with cannot connect to the multipass socket. Start it, then confirm: 
bashsudo launchctl kickstart -k system/com.canonical.multipassd
multipass list                       # prints a header, no socket error
Why: multipass runs a background daemon (multipassd) that owns the VMs. Every multipass command talks to it over a socket. kickstart -k restarts it under launchd.
Shortcut — helper scripts
The folder kube-lab/ holds ready-to-run scripts for these steps: launch.sh (V1+V2 on the host), prep-node.sh (runs inside each VM), and init-cp.sh (V3 on cp). Run bash kube-lab/launch.sh to do V1 and V2 in one command, or follow the manual steps below to learn each piece.

V1 · Launch two Ubuntu VMs

bashmultipass launch --name cp --cpus 2 --memory 2G --disk 12G 22.04
multipass launch --name w1 --cpus 2 --memory 2G --disk 12G 22.04

multipass list                       # note the cp IP (e.g. 192.168.64.x)
CP_IP=$(multipass info cp | awk '/IPv4/{print $2}')
echo "control plane IP = $CP_IP"
Why these flags
2 VMs give you one control plane (cp) and one worker (w1) — the minimum for a real join. 2 GB RAM each is enough for the control-plane pods plus a few workloads. You capture CP_IP now because kubeadm init and the worker join both need the control plane's real IP. A multipass VM has several interfaces, so you pin the right one instead of guessing.

V2 · Prepare both nodes (run on cp and w1)

Open a shell on each with multipass shell cp (and later w1), then run:

bashsudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay && sudo modprobe br_netfilter

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# Container runtime
sudo apt-get update && sudo apt-get install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd

# Kubernetes packages (arm64 works from pkgs.k8s.io)
sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.36/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.36/deb/ /' \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
Why each prep step
  • swapoff + strip fstab — the kubelet refuses to start with swap on. Kubernetes wants full control of memory scheduling. Removing the fstab line keeps swap off after reboot.
  • overlay + br_netfilter modules — overlay is the filesystem containerd layers images with. br_netfilter lets bridged pod traffic pass through iptables, so Services and NetworkPolicy work.
  • sysctl bridge-nf-call + ip_forward — makes bridged pod traffic visible to iptables (kube-proxy needs this) and turns the node into a router between pods. Skip it and pod-to-pod networking breaks silently.
  • containerd + SystemdCgroup=true — containerd is the container runtime (CRI). Its cgroup driver must match the kubelet's, which is systemd on Ubuntu. A mismatch causes random kubelet crashes — a classic exam gotcha.
  • apt-mark hold — pins the three packages so a routine apt upgrade can't jump a minor version and break the cluster. You upgrade on purpose with kubeadm upgrade (Lab H).

V3 · Initialize the control plane (on cp)

bashsudo kubeadm init --pod-network-cidr=192.168.0.0/16 --apiserver-advertise-address=$CP_IP

# Set up kubectl for your user
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

# Install Calico so nodes go Ready
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.1/manifests/calico.yaml

# Copy the printed "kubeadm join ..." command for the next step
Why each part of init
  • kubeadm init — bootstraps the control plane: generates certs and starts etcd, the API server, scheduler, and controller-manager as static pods.
  • --pod-network-cidr=192.168.0.0/16 — sets the pod IP range. It must match Calico's default, or pods get IPs the CNI will not route.
  • --apiserver-advertise-address=$CP_IP — pins the API server to the VM's real IP, so workers can reach it.
  • copy admin.conf to ~/.kube/config — this file is your cluster-admin credential. kubectl reads it to reach the API server.
  • Calico — a fresh cluster has no pod network, so nodes stay NotReady. Calico assigns pod IPs and enforces NetworkPolicy. Nodes flip to Ready soon after.

V4 · Join the worker (on w1)

bash# Paste the join command kubeadm printed (regenerate on cp if lost):
#   kubeadm token create --print-join-command
sudo kubeadm join $CP_IP:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>
Why the join needs a token and a hash
The token authenticates w1 to the control plane. The CA cert hash lets w1 verify it joins the right cluster, not a spoofed API server. This is the trust handshake. Tokens expire after 24h by default, so you regenerate rather than reuse: kubeadm token create --print-join-command.
Verify
On cp: kubectl get nodes shows cp and w1 both Ready after a minute. You built a cluster from scratch — the guide's kubeadm case, done for real.

Lab G · etcd Backup & Restore VMs

Run on the cp VM. This is a near-guaranteed exam task. A snapshot is a point-in-time copy of the whole cluster state.

Quick Reference — Copy & Go

bash# 1. Snapshot
sudo ETCDCTL_API=3 etcdctl snapshot save /opt/snap.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 2. Check it
sudo ETCDCTL_API=3 etcdctl snapshot status /opt/snap.db --write-out=table

# 3. Restore into a NEW data dir — never overwrite the live one
sudo ETCDCTL_API=3 etcdctl snapshot restore /opt/snap.db \
  --data-dir=/var/lib/etcd-restore

# 4. Point the static pod at it (edit the hostPath under etcd-data)
sudo vi /etc/kubernetes/manifests/etcd.yaml

Full walkthrough below, with verification after each step.

G1 · Install etcdctl and take a snapshot

bashsudo apt-get install -y etcd-client       # provides etcdctl

# Create something so you can prove the restore later
kubectl create deployment before-backup --image=nginx

sudo ETCDCTL_API=3 etcdctl snapshot save /opt/snap.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

sudo ETCDCTL_API=3 etcdctl snapshot status /opt/snap.db --write-out=table
Verify
The status table prints a hash, revision, and key count. The snapshot exists at /opt/snap.db.

G2 · Change something, then restore

bash# Make a change that the restore should erase
kubectl create deployment after-backup --image=nginx
kubectl get deploy      # both before-backup and after-backup exist

# Restore the snapshot into a NEW data directory
sudo ETCDCTL_API=3 etcdctl snapshot restore /opt/snap.db \
  --data-dir=/var/lib/etcd-restore

G3 · Point etcd at the restored data

bashsudo vi /etc/kubernetes/manifests/etcd.yaml
# Change the hostPath volume for etcd-data from /var/lib/etcd
# to /var/lib/etcd-restore (the 'path:' under volumes, name: etcd-data)

# The kubelet restarts etcd automatically. Watch it come back:
sudo crictl ps | grep etcd
kubectl get deploy
Verify
After etcd restarts, kubectl get deploy shows before-backup but not after-backup — the cluster jumped back to the snapshot moment.
Bonus — Same Idea on KinD
You can explore etcd on kind too: docker exec -it cka-control-plane bash, then find the etcd manifest under /etc/kubernetes/manifests/. The certs live in /etc/kubernetes/pki/etcd/. Snapshotting works if you install etcdctl in the container.

Lab H · Cluster Upgrade VMs

Upgrade one minor version, control plane first. Your cluster is on v1.36; upgrade to v1.37. This follows the order in the kubeadm upgrade documentation exactly.

The Drain Sits in the Middle
Run the drain after kubeadm upgrade apply or kubeadm upgrade node, and before you install the new kubelet. Do it in that order here, so your hands learn the order the exam expects.

H1 · Read the available versions (on cp)

bash# Point the package repo at the new minor version
sudo sed -i 's#/v1.36/#/v1.37/#' /etc/apt/sources.list.d/kubernetes.list
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.37/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg --yes
sudo apt-get update

# Copy the exact package string from this output, e.g. 1.37.0-1.1
sudo apt-cache madison kubeadm
Verify
apt-cache madison kubeadm lists 1.37.x-* rows. If it still shows only 1.36, the sed did not match. Open the file and check the URL by hand.

H2 · Upgrade the control plane (on cp)

bash# 1. Upgrade the kubeadm binary
sudo apt-mark unhold kubeadm && \
sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' && \
sudo apt-mark hold kubeadm
kubeadm version

# 2. Plan, then apply. 'plan' runs on the FIRST control plane node only.
sudo kubeadm upgrade plan
sudo kubeadm upgrade apply v1.37.x

# 3. Drain — after the apply, before the kubelet
kubectl drain cp --ignore-daemonsets --delete-emptydir-data

# 4. Upgrade kubelet and kubectl. kubeadm does NOT do this.
sudo apt-mark unhold kubelet kubectl && \
sudo apt-get update && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && \
sudo apt-mark hold kubelet kubectl

# 5. Restart the kubelet, then bring the node back
sudo systemctl daemon-reload
sudo systemctl restart kubelet
kubectl uncordon cp
Verify
kubectl get nodes shows cp at v1.37.x and Ready, with no SchedulingDisabled. If the kubelet does not start, read journalctl -xeu kubelet.

H3 · Upgrade the worker (on w1)

The worker uses kubeadm upgrade node, not kubeadm upgrade apply. There is no plan step. Everything else matches H2.

bash# On w1 — point the repo at v1.37 and upgrade kubeadm
sudo sed -i 's#/v1.36/#/v1.37/#' /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm='1.37.x-*' && sudo apt-mark hold kubeadm

# On w1 — update the local kubelet configuration
sudo kubeadm upgrade node

# On cp — drain the worker now, not before
kubectl drain w1 --ignore-daemonsets --delete-emptydir-data

# On w1 — kubelet and kubectl, then restart
sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload && sudo systemctl restart kubelet

# On cp
kubectl uncordon w1
Verify
kubectl get nodes shows both nodes at v1.37.x and Ready. You upgraded control plane before worker, one minor at a time — the exam's rules.

H4 · Break it on purpose, then recover

bash# Try to skip a minor version. kubeadm must refuse.
sudo kubeadm upgrade apply v1.39.0

# Forget the unhold. apt must refuse to change the version.
sudo apt-mark hold kubeadm
sudo apt-get install -y kubeadm='1.37.x-*'

# Leave a node cordoned, then find it
kubectl cordon w1
kubectl get nodes          # w1 shows SchedulingDisabled
kubectl uncordon w1
Verify
You saw three failures that cost real marks: the version skew refusal, the silent apt-mark hold refusal, and the forgotten uncordon. kubeadm upgrade apply is idempotent, so a failed run is safe to repeat.

Lab I · Static Pods & a Broken API Server VMs

Run on the cp VM. Static pods live on disk and are run directly by the kubelet — this is how the control plane itself starts.

I1 · Create a static pod

bash# Drop a manifest in the static pod directory
cat <<'EOF' | sudo tee /etc/kubernetes/manifests/static-web.yaml
apiVersion: v1
kind: Pod
metadata: { name: static-web }
spec:
  containers:
  - { name: web, image: nginx }
EOF
sleep 15
kubectl get pods -A | grep static-web
Verify
A pod named static-web-cp appears (the node name is appended). Delete the file and it disappears — the kubelet, not the API server, owns it.

I2 · Break and fix the API server

This Intentionally Breaks kubectl
Editing the api-server manifest wrong will make kubectl stop working for a minute. That is the lesson: you fix it on disk, not with kubectl. Do this only on the throwaway VM.
bashsudo cp /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/apiserver.bak
# Introduce a bad flag
sudo sed -i 's/- kube-apiserver/- kube-apiserver\n    - --this-flag-does-not-exist=true/' \
  /etc/kubernetes/manifests/kube-apiserver.yaml
sleep 30
kubectl get nodes                       # fails — api-server is crashing

# Diagnose below kubectl, with the container runtime
sudo crictl ps -a | grep apiserver
sudo crictl logs $(sudo crictl ps -a | grep apiserver | head -1 | awk '{print $1}') 2>&1 | tail -5

# Fix: restore the good manifest
sudo cp /tmp/apiserver.bak /etc/kubernetes/manifests/kube-apiserver.yaml
sleep 30
kubectl get nodes                       # works again
Verify
kubectl fails while the flag is bad, and recovers after you restore the file. You diagnosed a downed control plane with crictl — a real exam skill.

Common problems on Apple Silicon and their fixes.

SymptomCause & Fix
docker: cannot connect / kind create failsThe engine is not running. colima start. Confirm with docker info.
Nodes stuck NotReadyCalico is not installed or not Ready. Apply the Calico manifest and wait: kubectl -n kube-system rollout status ds/calico-node.
