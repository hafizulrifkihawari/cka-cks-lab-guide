CKS Study Guide / Overview & Exam Info

CKS Exam Overview

The Certified Kubernetes Security Specialist (CKS) is a hands-on exam testing your ability to harden Kubernetes clusters and workloads. It requires a valid CKA — complete that first.

How CKS Differs from CKA

CKA tests can you operate a cluster. CKS tests can you make it secure. Expect questions like:

  • Fix this pod so it runs as non-root with a read-only filesystem
  • Write a Falco rule to detect shell spawning inside containers
  • Scan this image for critical CVEs and replace it with a safer version
  • Create a NetworkPolicy that denies all egress except DNS
  • Enable audit logging and capture specific API server events
  • Apply an AppArmor profile to a pod

Learning Roadmap

CKS builds directly on CKA knowledge. Assume you know Kubernetes well — this guide focuses on the security layer on top. Budget 4–6 weeks with CKA already solid.

Required Background
Before starting CKS, you should be comfortable with: RBAC, NetworkPolicies, kubectl, YAML editing, Linux command line, and basic container security concepts (namespaces, capabilities, syscalls).

The 4Cs of Cloud Native Security

Kubernetes security is built in layers, one inside the next: Cloud → Cluster → Container → Code. Each layer sits inside the one before it, so a weak outer layer exposes everything within. The rule is defense in depth: secure every layer, and assume the layer outside it may already be breached. You cannot fix bad code with a firewall, and you cannot fix an open cluster with clean code — you need all four.

LayerWhat It CoversCKS Focus
CloudInfrastructure, IAM, network ACLsNode metadata protection, cloud provider access
ClusterK8s API, RBAC, network policiesHardening API server, etcd, admission controllers
ContainerContainer runtime, image, capabilitiesSecurityContext, AppArmor, seccomp, sandboxing
CodeApplication code, libraries, secretsStatic analysis, secret management, mTLS

Which Tool Defends Which Layer

CKS throws many tools at you. They stop feeling random once you see where each one works. Map every tool to the layer it protects, and you know which tool a task needs.

Cluster Setup

10% of exam — CIS benchmarks, TLS for Ingress, protecting node metadata, verifying platform binaries, and securing the GUI.

1. CIS Benchmark with kube-bench

kube-bench audits your cluster against the CIS Kubernetes Benchmark — the industry standard for K8s security configuration.

bash# Run kube-bench on control plane
kubectl apply -f https://raw.githubusercontent.com/aquasecurity/kube-bench/main/job-master.yaml

CheckFix

3. Protect Node Metadata

Cloud provider nodes expose a metadata API (e.g., 169.254.169.254 on AWS/GCP). Pods can reach it and potentially steal instance credentials. Block this with NetworkPolicy:

yamlapiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: block-metadata
spec:
  podSelector: {}   # all pods
  policyTypes: [Egress]
  egress:
  - to:
    - ipBlock:
        cidr: 0.0.0.0/0
        except:
        - 169.254.169.254/32   # AWS/GCP metadata endpoint

Cluster Hardening

15% of exam — Restricting API access, RBAC least privilege, ServiceAccount hardening, API server security flags, and etcd encryption at rest.

1. API Server Hardening

The API server manifest is at /etc/kubernetes/manifests/kube-apiserver.yaml. These flags matter for CKS:

FlagSecure ValueWhy
--anonymous-authfalseBlock unauthenticated requests
--insecure-port0Disable unencrypted HTTP port
--authorization-modeNode,RBACUse RBAC + Node authorization (never AlwaysAllow)
--enable-admission-pluginsSee belowEnable security admission controllers
--audit-log-path/var/log/k8s-audit.logEnable audit logging
--profilingfalseDisable profiling endpoints
--service-account-lookuptrueValidate SA tokens still exist in etcd

Key Admission Controllers

The Admission Chain — Where PSA, OPA & Image Policy Plug In
Every write request runs a gauntlet inside the API server before it is saved. First authentication (who are you?), then authorization (RBAC — are you allowed?), then admission control in two phases: mutating admission can change the object (add a default, inject a sidecar), then validating admission can accept or reject it. Only then does it reach etcd. This one pipeline is where most CKS controls live: Pod Security Admission, OPA/Gatekeeper, and image policy are all validating admission steps. Understand this chain and every one of those topics clicks into place.
# Recommended --enable-admission-plugins value
--enable-admission-plugins=NodeRestriction,\
  PodSecurity,\
  ResourceQuota,\
  LimitRanger,\
  ServiceAccount,\
  DefaultStorageClass,\
  MutatingAdmissionWebhook,\
  ValidatingAdmissionWebhook

# NodeRestriction prevents kubelets from modifying other nodes' objects
# PodSecurity enforces Pod Security Standards

kubelet Hardening

yaml# /var/lib/kubelet/config.yaml
authentication:
  anonymous:
    enabled: false     # no anonymous requests to kubelet API
  webhook:
    enabled: true
authorization:
  mode: Webhook         # not AlwaysAllow
readOnlyPort: 0          # disable unauthenticated read port
protectKernelDefaults: true

2. etcd Encryption at Rest

By default, Secrets are stored in plain text in etcd. Anyone who reads the etcd files or a snapshot sees every password. An EncryptionConfiguration tells the API server to encrypt Secrets before it writes them, and decrypt them when it reads. The data on disk becomes ciphertext; the key stays in a file only the API server reads.

yaml# /etc/kubernetes/enc/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:
      keys:
      - name: key1
        secret: <base64-encoded-32-byte-key>  # head -c 32 /dev/urandom | base64
  - identity: {}   # fallback: read unencrypted existing secrets
# Add to kube-apiserver.yaml:
--encryption-provider-config=/etc/kubernetes/enc/encryption-config.yaml

# Mount the file as a hostPath volume in the static pod manifest
# After enabling, re-encrypt all existing secrets:
kubectl get secrets --all-namespaces -o json | kubectl replace -f -

# Verify a secret is encrypted in etcd
ETCDCTL_API=3 etcdctl get /registry/secrets/default/my-secret \
  --cacert=... --cert=... --key=... | hexdump -C | head
# Should show encrypted bytes, not plain text

3. RBAC Hardening — Least Privilege

Dangerous RBAC Patterns to Eliminate
  • verbs: ["*"] — wildcard verbs, allows everything
  • resources: ["*"] — wildcard resources
  • cluster-admin bound to user/SA unnecessarily
  • Binding to the system:masters group
# Find overly permissive bindings
kubectl get clusterrolebindings -o wide
kubectl get rolebindings -A -o wide

# Find all subjects with cluster-admin
kubectl get clusterrolebindings -o json | \
  jq '.items[] | select(.roleRef.name=="cluster-admin") | .subjects'

# Check what permissions a SA has
kubectl auth can-i --list --as=system:serviceaccount:default:my-sa

4. ServiceAccount Token Hardening

By default, every pod gets a ServiceAccount token auto-mounted. This is a security risk if the app doesn't need to talk to the API server.

yaml# Disable auto-mount on the ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa
automountServiceAccountToken: false

---
# Or disable per-pod
spec:
  automountServiceAccountToken: false

Bound ServiceAccount Tokens (recommended)

K8s 1.20+ supports short-lived, audience-bound tokens via the TokenRequest API. Use projected volumes instead of the legacy auto-mounted token:

yamlvolumes:
- name: token
  projected:
    sources:
    - serviceAccountToken:
        audience: api
        expirationSeconds: 3600   # 1 hour, auto-rotated
        path: token

5. Upgrade Kubernetes Frequently

K8s releases patch CVEs regularly. Running an old version is a CKS failure in real life and the exam may test your upgrade knowledge. Follow the same kubeadm upgrade process from the CKA guide.

# Check current version and available upgrades
kubectl version

System Hardening

15% of exam — Reducing OS attack surface, Linux capabilities, AppArmor profiles, and seccomp syscall filtering.

1. Minimize OS Footprint

  • Remove unused packages: apt-get autoremove, audit with dpkg --list
  • Disable unnecessary services: systemctl disable --now snapd
  • Close unused ports: ss -tlnp to list, then disable services
  • Use minimal base images in containers (distroless, scratch, alpine)
# Check open ports on a node
ss -tlnp
netstat -tlnp   # alternative

# Check running services
systemctl list-units --type=service --state=running

# Remove a package
apt-get purge --auto-remove snapd
apt-get purge --auto-remove nfs-common

2. Linux Capabilities

Capabilities break up root's omnipotent privilege into discrete units. Containers by default get a subset of capabilities. CKS expects you to drop all and add only what's needed.

CapabilityWhat it allowsRisk
NET_ADMINModify network interfaces, routingHigh — network manipulation
SYS_ADMINWide range of system admin opsVery High — near root equivalent
CAP_SYS_PTRACETrace processesHigh — can read other process memory
NET_RAWRaw socket accessMedium — packet sniffing
yamlspec:
  containers:
  - name: app
    image: myapp
    securityContext:
      capabilities:
        drop: ["ALL"]       # drop everything first
        add: ["NET_BIND_SERVICE"]  # add only what's needed

3. AppArmor

AppArmor is a Linux Mandatory Access Control (MAC) system. Profiles define what files, capabilities, and syscalls a program can use. K8s can apply AppArmor profiles to containers.

Managing AppArmor Profiles

# Check AppArmor status on a node
apparmor_status
aa-status

# Load a profile
apparmor_parser -q /etc/apparmor.d/my-profile

# Check loaded profiles
cat /sys/kernel/security/apparmor/profiles

Example AppArmor Profile

apparmor# /etc/apparmor.d/k8s-deny-write
#include <tunables/global>

profile k8s-deny-write flags=(attach_disconnected) {
  #include <abstractions/base>

  file,             # allow all file reads
  deny /** w,       # deny all writes to filesystem
  deny /proc/* rw,  # deny /proc access

  network inet tcp,
  network inet udp,
}

Apply AppArmor Profile to a Pod

yamlmetadata:
  name: secure-pod
  annotations:
    # Format: container.apparmor.security.beta.kubernetes.io/<container-name>
    container.apparmor.security.beta.kubernetes.io/app: localhost/k8s-deny-write
spec:
  containers:
  - name: app   # must match the annotation container name
    image: nginx
AppArmor Must Be Loaded on the Node
The profile must be loaded on every node that the pod might be scheduled on before applying the annotation. Use a DaemonSet to distribute profiles, or ensure they're in your node image.

4. Seccomp

Seccomp (secure computing mode) filters syscalls a container can make. Blocks dangerous syscalls like ptrace, mount, unshare.

Built-in Profiles

ProfileEffect
RuntimeDefaultUse container runtime's default seccomp policy (recommended baseline)
UnconfinedNo seccomp filtering (default if not set)
Localhost/profile.jsonCustom profile from node's /var/lib/kubelet/seccomp/
yamlspec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault   # at pod level (all containers)
  containers:
  - name: app
    securityContext:
      seccompProfile:
        type: Localhost       # at container level (overrides pod)
        localhostProfile: profiles/audit.json   # relative to /var/lib/kubelet/seccomp/

Custom Seccomp Profile (audit mode)

json{
  "defaultAction": "SCMP_ACT_LOG",
  "syscalls": [
    {
      "names": ["chmod", "chown", "setuid", "setgid", "mount"],
      "action": "SCMP_ACT_ERRNO"
    }
  ]
}
Exam Pattern
A common exam task: "Apply the RuntimeDefault seccomp profile to all containers in this deployment." Just add the seccompProfile block to the pod spec's securityContext.

Minimize Microservice Vulnerabilities

20% of exam — SecurityContext hardening, Pod Security Admission, OPA/Gatekeeper, Secrets management, container sandboxing, and mTLS.

1. SecurityContext — Full Reference

The most exam-tested topic. Know every field cold.

yamlspec:
  securityContext:                    # pod-level (applies to all containers)
    runAsUser: 1000                   # UID for all containers
    runAsGroup: 3000                  # GID for all containers
    fsGroup: 2000                     # GID for mounted volumes
    runAsNonRoot: true                # prevents running as UID 0
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: myapp:1.0
    securityContext:                  # container-level (overrides pod-level)
      allowPrivilegeEscalation: false # no sudo/setuid binaries
      readOnlyRootFilesystem: true    # immutable container FS
      privileged: false               # not privileged (never set true in prod)
      runAsNonRoot: true
      runAsUser: 1000
      capabilities:
        drop: ["ALL"]
        add: ["NET_BIND_SERVICE"]
Most Common Exam Fix
"Harden this pod so it cannot write to its filesystem, cannot escalate privileges, and runs as non-root." Answer: set readOnlyRootFilesystem: true, allowPrivilegeEscalation: false, runAsNonRoot: true. If the app writes to disk, add an emptyDir volume for that specific path.

2. Pod Security Admission (PSA)

PSA replaced PodSecurityPolicy (removed in K8s 1.25). It enforces Pod Security Standards at the namespace level via labels.

Three Security Levels

LevelRestrictionsUse Case
privilegedNo restrictionsSystem namespaces (kube-system)
baselineBlocks known privilege escalations (no privileged pods, no hostPID, no hostNetwork)Most workloads
restrictedStrictest — requires non-root, drop all caps, no privilege escalation, seccomp runtime defaultSecurity-critical apps

Three Modes

ModeBehavior
enforceReject pods that violate the policy
auditAllow but log violations in audit log
warnAllow but send warning to user
# Apply PSA to a namespace using labels
kubectl label namespace prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/warn-version=latest

# Check what a pod would violate before applying
kubectl label namespace test pod-security.kubernetes.io/warn=restricted --dry-run=server

3. OPA Gatekeeper

Open Policy Agent (OPA) Gatekeeper provides policy-as-code for K8s using Rego language. It integrates as a ValidatingWebhookConfiguration.

Key Concepts

ObjectPurpose
ConstraintTemplateDefines a new CRD and the Rego policy logic
Constraint (instance)An instance of a ConstraintTemplate — where it applies and what parameters
yaml# ConstraintTemplate — defines the policy
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequiredlabels
spec:
  crd:
    spec:
      names:
        kind: K8sRequiredLabels
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package k8srequiredlabels
      violation[{"msg": msg}] {
        provided := {label | input.review.object.metadata.labels[label]}
        required := {label | label := input.parameters.labels[_]}
        missing := required - provided
        count(missing) > 0
        msg := sprintf("Missing required labels: %v", [missing])
      }
yaml# Constraint — enforces the policy
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: require-team-label
spec:
  match:
    kinds:
    - apiGroups: [""]
      kinds: ["Pod"]
  parameters:
    labels: ["team"]

4. Secrets Management Best Practices

  • Enable etcd encryption at rest (see Cluster Hardening section)
  • Use automountServiceAccountToken: false when not needed
  • Mount secrets as files (not env vars) — harder to accidentally leak in logs
  • Use external secrets managers (Vault, AWS Secrets Manager) with external-secrets-operator
  • Rotate secrets regularly; use short-lived tokens
# View a secret value (base64 encoded)
kubectl get secret db-secret -o jsonpath='{.data.password}' | base64 -d

# Check who has access to secrets
kubectl auth can-i get secrets --as=system:serviceaccount:default:my-sa

5. Container Runtime Sandboxes

Standard containers share the host kernel. Sandboxes add a stronger isolation layer for multi-tenant environments.

SandboxMechanismUse Case
gVisorUser-space kernel (runsc)Untrusted workloads, shared clusters
Kata ContainersLightweight VM per containerStrong isolation, compliance requirements
yaml# RuntimeClass for gVisor
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc   # must match runtime handler on nodes

---
# Use the RuntimeClass in a pod
spec:
  runtimeClassName: gvisor
  containers:
  - name: app
    image: nginx

Supply Chain Security

20% of exam — Image vulnerability scanning with Trivy, admission controllers, Dockerfile best practices, image signing, and static analysis.

1. Image Scanning with Trivy

Trivy is the most common image scanner in CKS. It scans images, filesystems, and IaC for vulnerabilities.

# Scan an image for vulnerabilities
trivy image nginx:1.25

# Filter by severity
trivy image --severity HIGH,CRITICAL nginx:1.25

# Scan and output as JSON
trivy image -f json -o results.json nginx:1.25

# Scan a local tarball
trivy image --input myimage.tar

# Scan a Dockerfile
trivy config ./Dockerfile

# Scan K8s manifests for misconfigs
trivy k8s --report summary cluster
Exam Pattern
"Scan image X and find the version with no HIGH or CRITICAL vulnerabilities." Use trivy image --severity HIGH,CRITICAL <image>. Then update the deployment's image to the safer version.

2. Dockerfile Best Practices

The exam may ask you to identify or fix insecure Dockerfile patterns.

Insecure Pattern

FROM ubuntu:latest
RUN apt-get install -y curl
USER root
COPY . /app
RUN chmod 777 /app
CMD ["./app"]

Hardened Pattern

FROM ubuntu:22.04   # pinned version
RUN apt-get install -y curl \
  && rm -rf /var/lib/apt/lists/*
RUN useradd -r -u 1001 appuser
COPY --chown=appuser:appuser . /app
USER 1001           # non-root
CMD ["./app"]
Bad PracticeRiskFix
FROM <image>:latestUnpredictable, may pull vulnerable imagePin exact version: nginx:1.25.3
USER rootContainer runs as rootCreate and use a non-root user
Secrets in DockerfileLeaked in image layersUse build args or secrets mounts (never ENV)
Unnecessary packagesLarger attack surfaceInstall only what's needed, clean cache
Large base imageMore CVEs, larger attack surfaceUse distroless or scratch images

Distroless Images

Distroless images contain only the application and its runtime dependencies — no shell, no package manager. Much smaller attack surface.

# Example: Go app with distroless base
FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o myapp

FROM gcr.io/distroless/static-debian12   # no shell, no package manager
COPY --from=builder /app/myapp /myapp
USER nonroot:nonroot
ENTRYPOINT ["/myapp"]

3. Admission Controllers for Image Policy

ImagePolicyWebhook

An admission controller that calls an external webhook to approve or deny image deployments.

yaml# admission-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: ImagePolicyWebhook
  configuration:
    imagePolicy:
      kubeConfigFile: /etc/kubernetes/admission/webhook-kubeconfig.yaml
      allowTTL: 50
      denyTTL: 50
      retryBackoff: 500
      defaultAllow: false   # deny if webhook is unreachable
# Add to kube-apiserver.yaml:
--admission-control-config-file=/etc/kubernetes/admission/admission-config.yaml
--enable-admission-plugins=...,ImagePolicyWebhook

ValidatingWebhookConfiguration

yamlapiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: image-policy
webhooks:
- name: validate.images.example.com
  rules:
  - apiGroups: [""]
    apiVersions: [v1]
    operations: [CREATE, UPDATE]
    resources: [pods]
  clientConfig:
    service:
      name: image-policy-svc
      namespace: kube-system
      path: /validate
    caBundle: <base64-ca-cert>
  failurePolicy: Fail   # Fail or Ignore
  admissionReviewVersions: [v1]
  sideEffects: None

Monitoring, Logging & Runtime Security

20% of exam — Falco for runtime threat detection, Kubernetes audit logs, immutable containers, and behavioral analysis.

1. Falco — Runtime Security

Falco monitors syscalls at the kernel level using eBPF/kernel module. It alerts when containers do suspicious things: spawn shells, read sensitive files, make unexpected network connections.

Falco Architecture

  • Falco engine: Reads syscall events from kernel driver
  • Rules: Define what constitutes suspicious behavior
  • Outputs: stdout, files, syslog, HTTP webhooks, Slack
# Install Falco (Helm)
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm install falco falcosecurity/falco --namespace falco --create-namespace

# Check Falco logs
kubectl logs -l app=falco -n falco -f

# On the host directly
systemctl status falco
journalctl -u falco -f

Falco Rule Structure

yaml# /etc/falco/rules.d/custom-rules.yaml
- rule: Shell Spawned in Container
  desc: Alert when a shell is spawned in any container
  condition: >
    spawned_process
    and container
    and proc.name in (shell_binaries)
    and not proc.pname in (shell_binaries)
  output: >
    Shell spawned in container
    (user=%user.name container=%container.name
     image=%container.image.repository:%container.image.tag
     shell=%proc.name parent=%proc.pname cmdline=%proc.cmdline)
  priority: WARNING
  tags: [container, shell, mitre_execution]
yaml# Rule to detect writing to /etc
- rule: Write to /etc in Container
  desc: Detect writes to /etc inside a container
  condition: >
    open_write
    and container
    and fd.name startswith /etc
  output: >
    File in /etc opened for write (user=%user.name
    command=%proc.cmdline file=%fd.name
    container=%container.name image=%container.image.repository)
  priority: ERROR

2. Kubernetes Audit Logging

Audit logs record every request to the API server: who did what, when, on which resource.

Audit Policy Levels

LevelWhat Gets Logged
NoneNothing
MetadataRequest metadata only (user, resource, verb) — no request/response body
RequestMetadata + request body
RequestResponseMetadata + request body + response body

Audit Policy File

yaml# /etc/kubernetes/audit/audit-policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
# Don't log read-only requests to non-sensitive resources
- level: None
  verbs: [get, list, watch]
  resources:
  - group: ""
    resources: [configmaps, endpoints]

# Log secret access at RequestResponse level
- level: RequestResponse
  resources:
  - group: ""
    resources: [secrets]

# Log all pod mutations
- level: Request
  verbs: [create, update, delete, patch]
  resources:
  - group: ""
    resources: [pods]

# Catch-all: metadata only for everything else
- level: Metadata

Enable Audit Logging on API Server

# Add to /etc/kubernetes/manifests/kube-apiserver.yaml:
--audit-policy-file=/etc/kubernetes/audit/audit-policy.yaml
--audit-log-path=/var/log/kubernetes/audit.log
--audit-log-maxage=30       # days to retain
--audit-log-maxbackup=10    # max backup files
--audit-log-maxsize=100     # MB per file

# Also mount the policy file and log directory as hostPath volumes
# in the static pod spec — both volumeMounts and volumes sections
# Read audit logs
tail -f /var/log/kubernetes/audit.log | jq .

# Find who deleted a pod
cat /var/log/kubernetes/audit.log | jq 'select(.verb=="delete" and .objectRef.resource=="pods")'

# Find secret access
cat /var/log/kubernetes/audit.log | jq 'select(.objectRef.resource=="secrets")'

3. Immutable Containers

Immutable containers cannot modify their filesystem at runtime. This prevents attackers from dropping malware or modifying configs post-compromise.

yamlspec:
  containers:
  - name: app
    image: myapp
    securityContext:
      readOnlyRootFilesystem: true   # immutable FS
    volumeMounts:
    - name: tmp
      mountPath: /tmp               # allow writes only here
    - name: cache
      mountPath: /var/cache
  volumes:
  - name: tmp
    emptyDir: {}
  - name: cache
    emptyDir: {}

Static Pod Manifests — Be Careful
When editing files in /etc/kubernetes/manifests/, a YAML syntax error will crash the API server and you'll have no kubectl access. Always back up the file first. If you break it: fix the YAML manually, then wait 30–60s for kubelet to restart the pod.

CKS-Specific Exam Mistakes

Top CKS Mistakes
  • Breaking the API server — bad YAML in kube-apiserver.yaml. Always backup first.
  • AppArmor profile not loaded on node — annotation without loaded profile is silently ignored or causes pod to fail
  • Wrong seccomp path — localhost profiles must exist in /var/lib/kubelet/seccomp/ relative path
  • Audit log missing volume mounts — policy file and log dir must be mounted into apiserver static pod
  • Forgetting to restart Falco after editing rules — changes won't take effect
  • NetworkPolicy with wrong namespace — policy only applies to pods in the namespace it's created in

Cluster Setup & Hardening

Run kube-bench and fix one failed control-plane check ~7 min

Task: Scan the control plane against the CIS benchmark. Fix one FAIL by editing an apiserver flag.

kube-bench run --targets master
# read a FAIL, then edit the flag it names:
vi /etc/kubernetes/manifests/kube-apiserver.yaml
# e.g. add --profiling=false ; kubelet restarts the static pod

Verify: re-run kube-bench; the check now passes.

Enable etcd encryption at rest for Secrets ~10 min

Task: Encrypt Secrets in etcd with an EncryptionConfiguration, then re-encrypt existing secrets.

# 1) write EncryptionConfiguration (aescbc) to /etc/kubernetes/enc/enc.yaml
# 2) add --encryption-provider-config to kube-apiserver.yaml + mount the path
# 3) re-encrypt what already exists:
kubectl get secrets -A -o json | kubectl replace -f -

Verify: ETCDCTL_API=3 etcdctl get /registry/secrets/... shows k8s:enc:aescbc, not plaintext.

Disable the default ServiceAccount token automount ~4 min

Task: Stop a pod from mounting a SA token it does not need.

# On the pod spec (preferred, explicit):
spec:
  automountServiceAccountToken: false
# Or on the ServiceAccount object itself

Verify: kubectl exec into the pod; /var/run/secrets/kubernetes.io/serviceaccount is absent.

Tighten an over-permissive ClusterRoleBinding ~5 min

Task: A ServiceAccount has cluster-admin. Grant it only read access to pods instead.

kubectl delete clusterrolebinding <too-broad-binding>
kubectl create clusterrole pod-viewer --verb=get,list,watch --resource=pods
kubectl create rolebinding sa-pods --clusterrole=pod-viewer \
  --serviceaccount=team:app-sa -n team
kubectl auth can-i '*' '*' --as=system:serviceaccount:team:app-sa   # should be no

Verify: the SA can list pods but cannot delete or create anything else.

System Hardening

Apply an AppArmor profile to a container ~6 min

Task: Load a profile on the node, then confine a pod's container with it.

# On the node: load the profile
apparmor_parser -q /etc/apparmor.d/k8s-deny-write
# On the container (K8s 1.30+ field):
securityContext:
  appArmorProfile:
    type: Localhost
    localhostProfile: k8s-deny-write

Verify: a blocked action (e.g. write to a denied path) fails inside the container.

Confine a pod with the RuntimeDefault seccomp profile ~4 min

Task: Apply the default seccomp filter to a pod.

spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault

Verify: kubectl get pod -o yaml shows the seccompProfile; the pod runs normally.

Drop all Linux capabilities, add only NET_BIND_SERVICE ~4 min

Task: Reduce a container to the minimum capability set.

securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]
  runAsNonRoot: true
  allowPrivilegeEscalation: false

Verify: the app binds port 80 but capsh --print in the container shows a minimal set.

Microservice & Supply Chain

Enforce the restricted Pod Security Standard on a namespace ~4 min

Task: Namespace prod must reject any pod that breaks the restricted standard.

kubectl label namespace prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted

Verify: a privileged pod is rejected; a compliant non-root pod is admitted.

Scan an image and pick a version with no HIGH/CRITICAL CVEs ~5 min

Task: Find a safe tag for an image, then update the deployment to it.

trivy image --severity HIGH,CRITICAL myapp:1.0
trivy image --severity HIGH,CRITICAL myapp:1.1   # compare tags
kubectl set image deployment/app app=myapp:1.1

Verify: the chosen tag reports 0 HIGH and 0 CRITICAL findings.

Block unsigned or untrusted images with an admission policy ~8 min

Task: Only allow images from a trusted registry. Use an ImagePolicyWebhook or an OPA/Gatekeeper constraint.

# Gatekeeper approach: ConstraintTemplate checks image prefix,
# then a Constraint enforces registry allow-list on Pods.
kubectl get constrainttemplates
kubectl describe <constraint>   # confirm it is enforced, not dry-run

Verify: a pod from an untrusted registry is denied at admission.
