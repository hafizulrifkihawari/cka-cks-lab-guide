Core Concepts

The foundation everything else builds on. Understand the architecture, objects, and kubectl before moving forward.

What Is a Kubernetes Cluster?

A cluster is a group of machines that work together as one computer. You do not log in to a machine and start a program. Instead, you tell the cluster what you want to run. The cluster decides where to run it, keeps it running, and restarts it if it dies.

You talk to the whole cluster through one API. That API is the same whether the cluster has 1 machine or 1,000. A machine in the cluster is called a node. Nodes come in two kinds: Control Plane nodes (the brain that makes decisions) and Worker nodes (the muscle that runs your apps).

Understand This
Think of Kubernetes as an operating system for a data center. A normal OS schedules processes onto CPU cores. Kubernetes schedules containers onto machines. You do not pick the core; you do not pick the machine. You state your intent, and the system places the work.

The Declarative Model — How Kubernetes Thinks

This is the single most important idea in Kubernetes. Learn it first.

You do not give step-by-step commands. You declare a desired state: "I want 3 copies of this web app." Kubernetes stores that wish. Small programs called controllers then work non-stop to make reality match your wish. If a pod dies and only 2 remain, a controller notices the gap and starts a 3rd. Nobody told it to — it simply keeps closing the difference between desired and actual.

Why This Matters for the Exam
Almost every troubleshooting task is a broken loop: desired state cannot be met. A pod is Pending because the scheduler cannot find a node that fits. A Deployment is stuck because a controller cannot pull an image. You fix the blocker, and the loop finishes the job for you.

Kubernetes Architecture

The control plane makes all decisions. The worker nodes carry them out. One component — the API server — sits in the middle. Every other part talks only to the API server, never directly to each other.

Control Plane Components — What Each One Really Does

kube-apiserver — the front door. Every command, every controller, every kubelet talks to it. It checks who you are (authentication), whether you are allowed (authorization), and whether the request is valid (admission). It is the only component that writes to etcd.

etcd — the memory. It stores every object in the cluster. If the API server is the front door, etcd is the filing cabinet behind it. Lose etcd and you lose the cluster — this is why backup is a core skill.

kube-scheduler — the placement engine. It only decides which node a new pod should run on. It does not start the pod; it writes its choice back through the API server. The kubelet does the starting.

kube-controller-manager — the worker bees. It runs the control loops: the ReplicaSet controller keeps pod counts right, the Node controller reacts to dead nodes, the Job controller runs jobs to completion, and many more.

cloud-controller-manager — the cloud adapter. It talks to AWS, GCP, or Azure to create load balancers and attach disks. On a bare-metal cluster it is not present.

ComponentOne-line roleAnalogy
kube-apiserverOnly entry point; validates and persists all requestsREST API gateway
etcdSource of truth for all cluster stateDatabase
kube-schedulerDecides which node each pod runs onPlacement engine
kube-controller-managerRuns the control loopsBackground daemons
cloud-controller-managerCreates cloud LoadBalancers and volumesCloud API adapter

Worker Node Components — What Each One Really Does

kubelet — the node's agent. It is the only thing that actually starts and stops pods on its node. It watches the API server for pods assigned to its node, tells the container runtime to run them, and reports their health back.

kube-proxy — the traffic cop. It programs iptables or IPVS rules so that a request to a Service's virtual IP lands on a real pod. It makes Services work.

Container Runtime (CRI) — the engine that pulls images and runs containers. Modern clusters use containerd. Docker is no longer used directly.

ComponentWhat it does
kubeletAgent on every node. Starts pods via the container runtime and reports status.
kube-proxyPrograms network rules (iptables/IPVS) so Services route to the right pods.
Container RuntimePulls images and runs containers. Usually containerd.
Where Control Plane Components Run
On clusters built with kubeadm, control plane components run as static pods in /etc/kubernetes/manifests/. The kubelet watches this directory and keeps them running. Check: kubectl get pods -n kube-system

What Is etcd, Really?

etcd is a distributed key-value store — a database that keeps small pieces of data safe across several machines. Kubernetes stores every object in it, under keys like /registry/pods/default/my-pod. When you run kubectl get pods, the API server reads from etcd. When you create something, the API server writes to etcd.

etcd keeps its copies in sync with the Raft protocol. Raft needs a majority (a quorum) to agree before it accepts a write. That is why production clusters run an odd number of etcd members (3 or 5): an odd count gives a clear majority and survives one or two failures.

Understand This
etcd is your cluster. Pods, Deployments, Secrets, RBAC rules — all of it lives in etcd and nowhere else. Back it up and you can rebuild the whole cluster. Lose it with no backup and the cluster is gone. This is exactly why the exam almost always asks you to snapshot and restore etcd.

Core API Objects

Pod

The smallest deployable unit. One or more containers sharing a network namespace and storage volumes. Pods are ephemeral — don't manage them directly, use controllers.

yamlapiVersion: v1

  name: my-pod
  labels:

  containers:

    resources:

Namespace

Virtual partitioning of a cluster. Resources in different namespaces are isolated by default (except networking). Most resources are namespaced; some (Nodes, PersistentVolumes, ClusterRoles) are cluster-scoped.

# Create namespace
kubectl create namespace dev

# Work in a namespace
kubectl get pods -n dev
kubectl get pods --all-namespaces   # or -A

# Set default namespace for current context
kubectl config set-context --current --namespace=dev

kubectl Essentials

The --dry-run=client -o yaml Pattern

The single most important kubectl trick for the exam. Generate YAML without creating the resource, then edit and apply.

# Generate a Pod YAML skeleton
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml

# Generate a Deployment YAML skeleton
kubectl create deployment web --image=nginx --replicas=3 --dry-run=client -o yaml > deploy.yaml

# Generate a Service YAML
kubectl expose deployment web --port=80 --type=ClusterIP --dry-run=client -o yaml

# Edit live resource in-place
kubectl edit deployment web

Imperative vs Declarative

Imperative (fast, exam-friendly)

kubectl run pod1 --image=nginx
kubectl create deployment d1 \
  --image=nginx --replicas=2
kubectl expose deployment d1 \
  --port=80

Declarative (production-grade)

kubectl apply -f deployment.yaml
kubectl apply -f ./manifests/
kubectl delete -f deployment.yaml

Labels & Selectors

Labels are key/value metadata. Selectors filter resources by labels. This is how Services find Pods and how Deployments own ReplicaSets.

# Add label
kubectl label pod my-pod env=prod

# Filter by label
kubectl get pods -l app=web
kubectl get pods -l 'env in (prod,staging)'

# Remove label
kubectl label pod my-pod env-
Key Insight
A Service routes to pods using a selector. If the selector doesn't match any pod labels, the service has no endpoints and traffic goes nowhere. This is a very common misconfiguration to debug.

2. How the Cluster Fits Together

A Kubernetes cluster has two kinds of machine. Beginners must hold this picture in mind before any command makes sense.

  • Control plane node — the brain. It runs the API server, the scheduler, the controller manager, and etcd. It decides what must run.
  • Worker node — the muscle. It runs the kubelet, the kube-proxy, and a container runtime. It runs the actual containers.

See diagram D1 in Core Concepts for the full component map. This page adds the part that diagram does not show: where the files live on disk. Almost every exam task in this domain ends in one of these paths. Learn the table, not the commands that print it.

/etc/kubernetes/pki/All TLS certificates and keys, including pki/etcd/A certificate expired. You need the etcd certs for a snapshot.

Why the Control Plane Runs as Static Pods
The API server, etcd, scheduler, and controller manager are plain YAML files in /etc/kubernetes/manifests/. The kubelet reads that folder from disk and runs whatever it finds there. It does not ask the API server for permission. This solves a chicken-and-egg problem: the cluster must start the API server, but you cannot use the API server to start the API server. Static pods let the cluster start itself.

Two consequences matter in the exam. First, you repair a dead API server by editing its file on disk, not with kubectl. Second, the kubelet applies your edit within seconds. You do not restart anything. You save the file and wait.

3. Step 1 — Prepare Every Machine

Run this section on every node, control plane and worker. Kubernetes refuses to install on an unprepared machine. Each step below has a reason. Learn the reason, because the exam shows you the symptom, not the step.

3.1 Turn swap off

The kubelet schedules pods against real memory. Swap makes memory accounting a lie, so a pod can exceed its limit and stay alive but slow. kubeadm therefore fails its preflight check when swap is on.

bash# Turn swap off now
swapoff -a

# Keep it off after a reboot: comment out the swap line in fstab
sed -i '/[[:space:]]swap[[:space:]]/s/^/#/' /etc/fstab

# Verify: this must print nothing
swapon --show
Common Mistake
Many guides tell you to sed -i '/swap/d' /etc/fstab. That deletes the line. Commenting the line is safer and reversible. Either way, you must edit /etc/fstab. If you only run swapoff -a, the node comes back with swap on after a reboot, and the kubelet stops.

3.2 Load the kernel modules

Kubernetes needs two kernel modules. overlay gives the container runtime its layered filesystem. br_netfilter lets iptables see traffic that crosses a Linux bridge, which is how pod traffic moves on a node.

bash# Load the modules at every boot
cat <<EOF | tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

# Load them now, without a reboot
modprobe overlay
modprobe br_netfilter

# Verify
lsmod | grep -E 'overlay|br_netfilter'

3.3 Set the sysctl parameters

These three settings let the node forward and filter pod traffic. Without them, Services fail and pods cannot reach each other across nodes.

bashcat <<EOF | tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

# Apply without a reboot
sysctl --system

# Verify
sysctl net.ipv4.ip_forward
What Each Setting Does
ip_forward — lets the node pass packets between interfaces. A node is a router for its pods. Without this, traffic dies at the node.
bridge-nf-call-iptables — sends bridged traffic through iptables. kube-proxy writes its Service rules into iptables. Without this, kube-proxy rules never match, and ClusterIP Services fail silently.
Set the modules first. The bridge-nf-call-* keys do not exist until br_netfilter is loaded.

3.4 Install a container runtime

Kubernetes does not run containers itself. It asks a runtime through the CRI (Container Runtime Interface). containerd is the usual choice. Docker Engine is not a CRI runtime and Kubernetes dropped direct support for it in v1.24.

bashapt-get update
apt-get install -y containerd

# Write the default configuration
mkdir -p /etc/containerd
containerd config default | tee /etc/containerd/config.toml

# Use the systemd cgroup driver
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

systemctl restart containerd
systemctl enable containerd
The Cgroup Driver Trap
The kubelet and the container runtime must use the same cgroup driver. Modern Linux uses systemd. The kubelet defaults to systemd. The containerd default file says SystemdCgroup = false, which means cgroupfs.

A mismatch produces a node that looks fine but cannot keep pods alive. Pods restart at random. The kubelet log shows cgroup errors. If a lab node behaves like this, check this setting first.

3.5 Install kubeadm, kubelet, and kubectl

These three packages come from the pkgs.k8s.io repository. Each repository URL serves exactly one minor version. To install a different minor version, you change the URL.

bash# Add the repository key
apt-get install -y apt-transport-https ca-certificates curl gpg
mkdir -p /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.36/deb/Release.key \
  | gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

# Add the repository itself
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.36/deb/ /' \
  | tee /etc/apt/sources.list.d/kubernetes.list

apt-get update
apt-get install -y kubelet kubeadm kubectl

# Stop apt from upgrading them by accident
apt-mark hold kubelet kubeadm kubectl

# Verify
kubeadm version
kubelet --version

4. Step 2 — Create the Control Plane with kubeadm

What is kubeadm? Building a cluster by hand means creating a private certificate authority, issuing a dozen certificates, writing configuration for five components, and wiring them together. That work is slow and easy to get wrong. kubeadm does all of it for you, in the way the project recommends. You run kubeadm init once on the first control plane node, then kubeadm join on every other node.

Here is what kubeadm init does, in order:

4.1 Run kubeadm init

bashkubeadm init \
  --apiserver-advertise-address=192.168.56.10 \
  --pod-network-cidr=10.244.0.0/16 \
  --kubernetes-version=v1.36.0
FlagMeaningWhen you need it
--apiserver-advertise-addressThe node IP that other nodes use to reach the API server.Set it when the node has more than one network interface. kubeadm otherwise guesses, and may pick the wrong one.
--pod-network-cidrThe IP range that pods get.Required by some CNI plugins. Flannel expects 10.244.0.0/16. Calico defaults to 192.168.0.0/16. The value must match the CNI manifest you apply next.
--kubernetes-versionThe exact control plane version to install.Use it to pin the version. Without it, kubeadm installs the newest patch of its own minor version.
--control-plane-endpointA DNS name or load balancer address for the control plane.Required for a highly available cluster. See Section 7.
--cri-socketThe runtime socket path.Only when more than one runtime is installed. Example: unix:///run/containerd/containerd.sock.
Save the Join Command
kubeadm init prints a kubeadm join line at the end. Copy it somewhere safe. The token in it expires after 24 hours. If you lose it, do not panic — Section 6 shows you how to print a new one.

4.2 Set up your kubeconfig

The cluster now runs, but kubectl does not know how to reach it or how to prove who you are. kubeadm init wrote an administrator kubeconfig to /etc/kubernetes/admin.conf. Copy it to your home directory.

bashmkdir -p $HOME/.kube
cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
chown $(id -u):$(id -g) $HOME/.kube/config

# As root, this single line also works
export KUBECONFIG=/etc/kubernetes/admin.conf

# Verify
kubectl get nodes
Recovery Tip
If kubectl ever says "The connection to the server localhost:8080 was refused", it means kubectl found no kubeconfig at all. It fell back to its built-in default. Point KUBECONFIG at /etc/kubernetes/admin.conf and try again. This one message explains most "the cluster is dead" panics.

4.3 Expect NotReady — that is correct

bash$ kubectl get nodes
NAME           STATUS     ROLES           AGE   VERSION
controlplane   NotReady   control-plane   45s   v1.36.0

The node reports NotReady because no pod network exists yet. CoreDNS also stays Pending for the same reason. Install a CNI plugin next and both problems clear.

5. Step 3 — Install a CNI Plugin

Kubernetes defines a network model but ships no implementation. A CNI plugin supplies the implementation. It gives every pod an IP address and makes every pod reachable from every other pod without network address translation.

bash# Flannel — simplest, needs --pod-network-cidr=10.244.0.0/16
kubectl apply -f https://github.com/flannel-io/flannel/releases/latest/download/kube-flannel.yml

# OR Calico — supports NetworkPolicy, default CIDR 192.168.0.0/16
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/calico.yaml

# Watch the nodes turn Ready (30-90 seconds)
kubectl get nodes -w

# Confirm CoreDNS is now Running

7. A Highly Available Control Plane

One control plane node is one point of failure. Lose it and you lose etcd, so you lose the cluster. A highly available control plane runs three control plane nodes behind one address.

Why three, and not two? etcd makes decisions by majority vote, called a quorum. A cluster of n members needs (n/2)+1 members alive. Three members tolerate one failure. Two members tolerate none, because one of two is not a majority. Always use an odd number: 3 or 5.

TopologyWhere etcd runsTrade-off
Stacked etcdOn the same nodes as the control planeFewer machines and simpler. Losing one node loses both a control plane and an etcd member.
External etcdOn its own dedicated machinesFailures stay separate. Needs at least three extra machines and more work.

7.1 Build a stacked HA cluster

bash# 1. On the FIRST control plane node

  --control-plane-endpoint "k8s-api.example.com:6443" \
  --upload-certs \
  --pod-network-cidr=192.168.0.0/16

# 2. Install the CNI plugin
kubectl apply -f <cni-manifest>

# 3. On EACH other control plane node — note --control-plane
kubeadm join k8s-api.example.com:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>

# 4. Workers join the same endpoint, without --control-plane
kubeadm join k8s-api.example.com:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>

8. Upgrade the Cluster

An upgrade appears in almost every CKA sitting. The order never changes. Learn the order first, then the commands.

  1. Upgrade the first control plane node: kubeadm → kubeadm upgrade plan → kubeadm upgrade apply → drain → kubelet and kubectl → restart → uncordon.
  2. Upgrade any other control plane node: kubeadm → kubeadm upgrade node → drain → kubelet and kubectl → restart → uncordon.
  3. Upgrade the workers, one at a time. A worker uses the same steps as step 2.
Where the Drain Goes — Read This Twice
Drain the node after you run kubeadm upgrade apply or kubeadm upgrade node, and before you install the new kubelet. Many older guides drain first. The Kubernetes documentation puts the drain between those two steps, because kubeadm upgrade only rewrites static pod manifests and configuration. The workload must leave the node before the kubelet itself restarts.
Why These Rules Exist
Control plane first. The API server must be the same version as, or newer than, every component that talks to it. Upgrade a kubelet past its API server and the kubelet may send a request the API server cannot answer.

One minor version at a time. Kubernetes promises compatibility only across a small gap, called the version skew policy. kubeadm enforces it. A jump from 1.35 to 1.37 is refused. Do 1.35 → 1.36, then 1.36 → 1.37.

Drain for a minor version. A minor version change of the kubelet needs a drain. A drain moves the running pods to other nodes first. The kubelet then restarts with nothing live on the node.
ComponentAllowed difference from kube-apiserver
kube-controller-manager, kube-schedulerSame version, or one minor version older
kubeletUp to three minor versions older. Never newer.
kubectlOne minor version newer or older

8.1 Check these before you start

  • The cluster uses static control plane and etcd pods, or an external etcd.
  • Swap is off on every node you touch.
  • You read the release notes for the target version.
  • You backed up anything the cluster does not hold, such as application databases. kubeadm upgrade does not touch your workloads, but a drain restarts them.
  • The upgrade crosses one minor version only. kubeadm refuses a larger jump.

8.2 Find the target version

Each pkgs.k8s.io repository URL serves exactly one minor version. To cross a minor version, point the repository at the new minor version first.

bash# Debian, Ubuntu — point the repo at the NEW minor version
sudo sed -i 's|/v1.36/|/v1.37/|' /etc/apt/sources.list.d/kubernetes.list
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.37/deb/Release.key \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg --yes
sudo apt-get update

# Now list the exact package strings available
sudo apt-cache madison kubeadm
# Read the latest 1.37.x-* line. Copy that string.
bash# CentOS, RHEL, Fedora — DNF4 (Fedora < 41, RHEL/CentOS < 10)
sudo dnf list --showduplicates kubeadm --disableexcludes=kubernetes

# CentOS, RHEL, Fedora — DNF5
sudo dnf list --showduplicates kubeadm --setopt=disable_excludes=kubernetes
The Version String Has a Suffix
The pkgs.k8s.io repository uses the format 1.37.0-1.1. The old 1.37.0-00 format no longer exists. Never type the version from memory. Run apt-cache madison kubeadm and copy the exact string. The commands below write it as 1.37.x-*; replace x with the patch number you found.

8.3 Upgrade the first control plane node

bash# 1. Upgrade the kubeadm binary itself
sudo apt-mark unhold kubeadm && \
sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' && \
sudo apt-mark hold kubeadm

kubeadm version              # confirm before you continue

# 2. See what will change. This is read-only and safe.
sudo kubeadm upgrade plan

# 3. Apply the control plane upgrade. Run this on the FIRST node only.
sudo kubeadm upgrade apply v1.37.x

# 4. Drain the node (run where kubectl works)
kubectl drain <node-to-drain> --ignore-daemonsets --delete-emptydir-data

# 5. Upgrade kubelet and kubectl — kubeadm does NOT do this
sudo apt-mark unhold kubelet kubectl && \
sudo apt-get update && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && \
sudo apt-mark hold kubelet kubectl

# 6. Restart the kubelet
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# 7. Let the node take pods again
kubectl uncordon <node-to-drain>

# 8. Verify
kubectl get nodes
Package Manager Equivalents
DNF4: sudo dnf install -y kubeadm-'1.37.x-*' --disableexcludes=kubernetes
DNF5: sudo dnf install -y kubeadm-'1.37.x-*' --setopt=disable_excludes=kubernetes
Hold on RPM systems: sudo yum versionlock kubeadm kubelet kubectl. Release it with sudo yum versionlock delete kubeadm kubelet kubectl.

8.4 Upgrade every other control plane node

Two things change on the second and later control plane nodes. You skip kubeadm upgrade plan. You run kubeadm upgrade node instead of kubeadm upgrade apply. Everything else matches.

bash# On the target node — upgrade kubeadm first
sudo apt-mark unhold kubeadm && \
sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' && \
sudo apt-mark hold kubeadm

# Upgrade this control plane node. No version argument.
sudo kubeadm upgrade node

# Drain, then upgrade kubelet and kubectl
kubectl drain <node-to-drain> --ignore-daemonsets --delete-emptydir-data
sudo apt-mark unhold kubelet kubectl && \
sudo apt-get update && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && \
sudo apt-mark hold kubelet kubectl

sudo systemctl daemon-reload
sudo systemctl restart kubelet
kubectl uncordon <node-to-drain>

8.5 Upgrade the worker nodes

A worker uses the same six steps as a second control plane node. Do one worker at a time. Wait for the node to report Ready before you start the next one.

bash# 1. On the worker — upgrade kubeadm
sudo apt-mark unhold kubeadm && \
sudo apt-get update && sudo apt-get install -y kubeadm='1.37.x-*' && \
sudo apt-mark hold kubeadm

# 2. Update the local kubelet configuration
sudo kubeadm upgrade node

# 3. Drain the worker (run where kubectl works)
kubectl drain <node-to-drain> --ignore-daemonsets --delete-emptydir-data

# 4. Upgrade kubelet and kubectl on the worker
sudo apt-mark unhold kubelet kubectl && \
sudo apt-get update && sudo apt-get install -y kubelet='1.37.x-*' kubectl='1.37.x-*' && \
sudo apt-mark hold kubelet kubectl

# 5. Restart the kubelet
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# 6. Bring the worker back
kubectl uncordon <node-to-drain>
Every Container Restarts
The upgrade changes the container spec hash. Every container on the node therefore restarts. This is expected. It is not a fault.

8.7 Recover from a failed upgrade

  • kubeadm upgrade apply is idempotent. If it fails part way, run it again.
  • If the kubelet does not start, read journalctl -xeu kubelet first. A wrong version string is the usual cause.
  • If a node stays drained, run kubectl uncordon <node>.
  • To roll back, install the previous package versions with the same apt-mark unhold and apt-get install pattern.
Upgrading etcd — Stop the API Server First
A restart of etcd stalls the requests the API server holds open. To avoid that, shut the API server down gracefully before the upgrade command.

Read the Error, Then Add the Flag
A plain kubectl drain usually fails on the first try. The error names the cause. Add only the flag that matches it.
"cannot delete DaemonSet-managed Pods" → add --ignore-daemonsets.
"cannot delete Pods with local storage" → add --delete-emptydir-data.
"cannot delete Pods not managed by ..." → add --force. This deletes the pod for good, because nothing will recreate it.

A drain also respects any PodDisruptionBudget. If evicting one more pod would break the budget, the drain waits instead of harming the application. A drain that hangs forever usually means a PDB blocks it.

9.2 Certificate renewal

kubeadm issues client and server certificates that expire after one year. An expired certificate stops kubectl and stops the control plane components from talking to each other. kubeadm renews the certificates automatically during a cluster upgrade, which is why regularly upgraded clusters rarely hit this. A cluster left alone for a year does hit it.

bash# Show every certificate and its expiry date
kubeadm certs check-expiration

kubeadm certs renew all

10. etcd Backup and Restore

etcd is the only place cluster state lives. Every Deployment, Secret, and ConfigMap is a key in etcd. Lose etcd and you lose the cluster, even though the containers keep running for a while.

What a Snapshot and a Restore Really Do
A snapshot is one point-in-time copy of the whole etcd database. It is a single file.

A restore unpacks that file into a new, empty data directory on disk. It does not touch the running etcd. Nothing changes yet. You then edit the etcd static pod manifest to point at the new directory. The kubelet sees the edit, restarts etcd, and etcd loads the restored data. The cluster jumps back to the moment of the snapshot.

This is also why backup needs certificates and restore does not. A backup talks to the live etcd over TLS, so it needs the endpoint and three certificate files. A restore only writes files on disk, so it needs none of them.

11. RBAC — Role-Based Access Control

Every request to the API server passes three gates in order.

  1. Authentication — who are you? A client certificate, a token, or a ServiceAccount token proves identity.
  2. Authorization — may you do this? This is RBAC's job.
  3. Admission control — should this object be changed or rejected? Quotas and policies act here.

RBAC answers gate 2 by asking four questions:

  • Who — the subject: a User, a Group, or a ServiceAccount.
  • What action — the verb: get, list, watch, create, update, patch, delete.
  • On what — the resource: pods, deployments, secrets.
  • Where — one namespace, or the whole cluster.

A Role is a list of permissions. It names no people. A Binding connects people to a Role. This split lets one Role serve many subjects.

ObjectScopePurpose
RoleNamespacedPermissions inside one namespace
ClusterRoleCluster-widePermissions across all namespaces, or on cluster-scoped resources such as nodes and PersistentVolumes
RoleBindingNamespacedGrants a Role or a ClusterRole to subjects, inside one namespace
ClusterRoleBindingCluster-wideGrants a ClusterRole everywhere
The Four Rules That Explain Every RBAC Question
1. Permissions are additive only. RBAC has no deny rule. A subject may act if any binding allows it. To remove access, you delete a binding.
2. A RoleBinding can point at a ClusterRole. The permissions then apply only inside that binding's namespace. This is the normal way to reuse one ClusterRole in many namespaces.
3. A ClusterRoleBinding always grants cluster-wide. You cannot narrow it to a namespace.
4. Cluster-scoped resources need a ClusterRole. Nodes, PersistentVolumes, and namespaces themselves do not live in a namespace, so a Role can never grant access to them.

A ServiceAccount is an identity for a process inside a pod, not for a person. Every pod gets one. If you do not name one, the pod uses the default ServiceAccount of its namespace, which has almost no permissions.

12. Create Access for a New User

Kubernetes has no User object. You cannot run kubectl create user. A "user" is simply a name that the authentication layer reports. With the default kubeadm setup, that name is the Common Name (CN) of a client certificate signed by the cluster CA, and the groups are the Organization (O) fields.

This task appears in the exam. Follow the four steps.

bash# STEP 1 — the user creates a private key and a signing request
openssl genrsa -out jane.key 2048
openssl req -new -key jane.key -out jane.csr -subj "/CN=jane/O=developers"

# STEP 2 — wrap the request in a CertificateSigningRequest object
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: jane
spec:
  request: $(cat jane.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  expirationSeconds: 86400
  usages:
  - client auth
EOF

# STEP 3 — approve it, then extract the signed certificate
kubectl get csr
kubectl certificate approve jane
kubectl get csr jane -o jsonpath='{.status.certificate}' | base64 -d > jane.crt

# STEP 4 — build a kubeconfig entry and grant permissions
kubectl config set-credentials jane --client-key=jane.key --client-certificate=jane.crt --embed-certs=true
kubectl config set-context jane-context --cluster=kubernetes --user=jane --namespace=dev

kubectl create role pod-reader --verb=get,list,watch --resource=pods -n dev
kubectl create rolebinding jane-pod-reader --role=pod-reader --user=jane -n dev

# Verify
kubectl auth can-i list pods --as=jane -n dev
kubectl --context=jane-context get pods -n dev
Three Traps in This Flow
1. request: must be the base64 of the CSR with no line breaks. The tr -d '\n' is not optional.
2. signerName must be kubernetes.io/kube-apiserver-client for a user certificate. Another signer produces a certificate the API server will not accept.
3. Approving the CSR only proves identity. It grants nothing. You still need a Role and a binding.

15. CRDs and Operators

A CustomResourceDefinition (CRD) teaches the API server a new kind of object. After you install a CRD, the new kind behaves like a built-in one: kubectl get, kubectl describe, RBAC, and labels all work on it.

A CRD by itself only stores data. An Operator adds the behaviour. An operator is a controller in a pod. It watches the custom resources and makes reality match them, exactly as the built-in controllers do for Deployments.

yamlapiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.stable.example.com   # must be <plural>.<group>
spec:
  group: stable.example.com
  scope: Namespaced                   # or Cluster
  names:
    plural: backups
    singular: backup
    kind: Backup
    shortNames: [bk]
  versions:
  - name: v1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            properties:
              schedule: { type: string }
bash# What custom types does this cluster already know?
kubectl get crd
kubectl get crd <name> -o yaml

# Install a CRD or an operator bundle
kubectl apply -f https://example.com/operator.yaml

# Use the new type
kubectl api-resources | grep stable.example.com
kubectl explain backup.spec
kubectl get backups -A

# Check the operator itself is healthy
kubectl get pods -n <operator-namespace>
kubectl logs -n <operator-namespace> deploy/<operator-name>

# Remove a CRD — this deletes EVERY object of that type
kubectl delete crd backups.stable.example.com
Deleting a CRD Deletes the Data
Removing a CustomResourceDefinition removes every custom object that used it, across every namespace, with no warning and no undo. Check what exists first: kubectl get <plural> -A.

The exam is unlikely to ask you to write a CRD from an empty file. It may ask you to install an operator from a URL or a Helm chart, then confirm it works, or to find which CRDs a cluster has. Deployments

The standard way to run stateless apps. Manages ReplicaSets, handles rolling updates and rollbacks.

The Controller Idea — Why You Rarely Create Pods Directly
You almost never create a bare Pod. You create a Deployment. The Deployment creates a ReplicaSet. The ReplicaSet creates the Pods. Each layer is its own control loop watching the layer below. Kill a pod and the ReplicaSet makes a new one. Change the image and the Deployment builds a new ReplicaSet, then shifts pods from old to new — one at a time — so the app never fully goes down. That shift is a rolling update.
# Create
kubectl create deployment web --image=nginx:1.25 --replicas=3

# Scale
kubectl scale deployment web --replicas=5

kubectl set image deployment/web nginx=nginx:1.26

# Check rollout status
kubectl rollout status deployment/web

# View history
kubectl rollout history deployment/web

# Rollback to previous version
kubectl rollout undo deployment/web

# Rollback to specific revision
kubectl rollout undo deployment/web --to-revision=2

Resource Requests & Limits

Request: minimum guaranteed. Used by scheduler for placement.
Limit: maximum. Pod is OOMKilled if memory exceeds limit; CPU is throttled.

LimitRange
Set default requests/limits for a namespace so unspecified pods don't starve or hog resources.
yamlapiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: dev
spec:
  limits:
  - default:
      cpu: 500m
      memory: 128Mi
    defaultRequest:
      cpu: 100m
      memory: 64Mi
    type: Container

Quality of Service (QoS) Classes

Kubernetes reads a pod's requests and limits and sorts it into one of three QoS classes. You do not set the class — it is derived. It decides who gets killed first when a node runs out of memory.

ClassHow a pod qualifiesEvicted under memory pressure
GuaranteedEvery container sets requests equal to limits (CPU and memory)Last — most protected
BurstableAt least one container has a request or limit, but not GuaranteedSecond
BestEffortNo requests or limits anywhereFirst — killed soonest
# See a pod's QoS class
kubectl get pod my-pod -o jsonpath='{.status.qosClass}'
Why This Matters
When a node is out of memory, the kubelet must evict pods to survive. It removes BestEffort first, then Burstable, then Guaranteed. So a critical pod should set requests equal to limits to earn the Guaranteed class. This also explains a "random" pod eviction: the node was under pressure and picked the lowest QoS class.

ResourceQuota

A ResourceQuota caps the total resources a whole namespace may use — a team-level budget. It limits both compute totals and object counts. When a namespace hits its quota, new objects that would exceed it are rejected.

yamlapiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    configmaps: "10"
LimitRange vs ResourceQuota
LimitRange works per pod/container — it sets defaults and min/max bounds for each one. ResourceQuota works per namespace — it caps the grand total. They pair well: LimitRange fills in requests so ResourceQuota can count them. Note once a quota sets requests.cpu, every new pod must declare that request or it is rejected — this is a classic exam trap.

Taints, Tolerations & Node Affinity

How scheduling works. When a pod is created, the scheduler runs two steps. First it filters: it throws out every node that does not fit — not enough CPU/memory, a taint the pod does not tolerate, a nodeSelector that does not match. Then it scores the survivors and picks the best one. The tools below are how you steer that decision.

Taints & Tolerations

Taints repel pods from nodes. Tolerations allow pods to be scheduled on tainted nodes.

# Taint a node
kubectl taint node worker-1 key=value:NoSchedule
kubectl taint node worker-1 key=value:NoExecute    # evicts existing pods too
kubectl taint node worker-1 key=value:PreferNoSchedule

# Remove a taint
kubectl taint node worker-1 key=value:NoSchedule-
yaml# Add toleration to a pod to allow scheduling on the tainted node
spec:
  tolerations:
  - key: "key"
    operator: "Equal"
    value: "value"
    effect: "NoSchedule"

Node Affinity

More expressive than nodeSelector. Allows required vs preferred scheduling.

yamlspec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values: [ssd]
Taint vs Affinity
Taint/toleration: node pushes away pods (node-driven). Node affinity: pod pulls toward nodes (pod-driven). Use both together for strict placement requirements.

Pod Priority & Preemption

Not all pods are equally important. A PriorityClass gives a pod a number: higher means more important. This changes what happens when the cluster is full. If a high-priority pod cannot find a node, the scheduler does not just leave it Pending — it preempts: it evicts one or more lower-priority pods to free room, then schedules the important one.

yamlapiVersion: scheduling.k8s.io/v1
kind: PriorityClass

PodDisruptionBudget (PDB)

A running app faces two kinds of trouble. Involuntary disruptions just happen — a node crashes, hardware dies. You cannot negotiate with those. Voluntary disruptions are ones you trigger — most importantly kubectl drain during a node upgrade. A PodDisruptionBudget protects you from the voluntary kind: it tells Kubernetes the minimum service you must keep while pods are being moved.

You set either minAvailable (keep at least N running) or maxUnavailable (take down at most N at a time). A drain then evicts pods slowly enough to respect the budget — and if it cannot, the drain blocks rather than break your app.

yamlapiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2          # or use maxUnavailable: 1
  selector:
    matchLabels:
      app: web
Why a Drain Sometimes Hangs
If kubectl drain seems stuck, a PDB is often the reason — draining more pods would drop you below minAvailable, so Kubernetes waits. That is the PDB doing its job. To finish, scale the app up first, fix the PDB, or (with care) drain another node. This links straight to the Cluster → Cluster Upgrade section: a PDB is exactly what makes a rolling node upgrade safe.

Init & Sidecar Containers

Init containers run to completion before app containers start. A native sidecar is an init container with restartPolicy: Always (stable in Kubernetes 1.29+). It starts before the app container and keeps running beside it.

yamlspec:
  initContainers:
  - name: init-db       # runs first, then exits
    image: busybox
    command: ["sh", "-c", "until nslookup db; do sleep 2; done"]
  - name: log-shipper   # native sidecar — stays running
    image: fluentd:latest
    restartPolicy: Always
  containers:
  - name: app
    image: myapp

Health Probes

Kubernetes cannot read your app's mind. A container can be running yet be broken — still booting, deadlocked, or not ready for traffic. Probes are small checks the kubelet runs to learn the real health of a container. There are three, and each has a different job.

ProbeQuestion it answersWhat happens on failure
startupProbeHas the app finished booting?Holds off the other two probes. Protects slow-starting apps.
readinessProbeIs it ready for traffic?Pod is removed from the Service Endpoints — no restart.
livenessProbeIs it still alive?The kubelet restarts the container.
yamlcontainers:
- name: app
  image: myapp
  startupProbe:            # give slow apps time to boot
    httpGet: { path: /healthz, port: 8080 }
    failureThreshold: 30
    periodSeconds: 10     # up to 300s to start
  readinessProbe:          # controls Service traffic
    httpGet: { path: /ready, port: 8080 }
    initialDelaySeconds: 5
    periodSeconds: 5
  livenessProbe:           # restarts a stuck container
    tcpSocket: { port: 8080 }
    periodSeconds: 10
    failureThreshold: 3

A probe can check health three ways: httpGet (a 2xx/3xx response is healthy), exec (a command that exits 0 is healthy), or tcpSocket (the port opens).

The Gotcha Everyone Trips On
Readiness pulls you out of traffic. Liveness restarts you. Mix them up and you cause outages. If you put a heavy check on liveness, a slow app gets killed and restarted forever (CrashLoop). If a dependency is down, use readiness so the pod leaves the load balancer but keeps running — do not use liveness, or you restart a healthy app for no reason.

Services & Networking

20% of exam — Service types, Ingress, CoreDNS, NetworkPolicies. Networking is heavily tested; understand how traffic flows end-to-end.

The Four Networking Problems Kubernetes Solves
1. Container ↔ container inside one pod — they share a network, so they reach each other on localhost. 2. Pod ↔ pod — every pod gets its own IP and can reach every other pod directly, on any node. This flat network is provided by the CNI plugin (Calico, Cilium, Flannel). 3. Pod ↔ Service — pods are ephemeral, so a Service gives a stable address. 4. External ↔ Service — NodePort, LoadBalancer, and Ingress let the outside world in.

Services

A stable virtual IP (ClusterIP) that load-balances traffic to matching pods. Pods come and go; the Service IP stays constant.

Why Services exist. A pod's IP changes every time it restarts. If your frontend hard-coded a backend pod's IP, it would break constantly. A Service is a fixed name and virtual IP that always points at the live pods. It finds them with a label selector, and the list of matching pods is stored in an Endpoints object. If the selector matches no pods, Endpoints is empty and traffic goes nowhere — the number-one Service bug.

Ingress

HTTP/HTTPS routing rules. Requires an Ingress Controller (NGINX, Traefik, etc.) to be installed in the cluster.

This is north-south traffic — from outside the cluster to your pods. Follow the path: a user's request hits a cloud LoadBalancer, which sends it to the Ingress controller running in the cluster. The controller reads your Ingress rules (which host and path go where) and forwards the request to the right Service, which then reaches a Pod.

Ingress Controller vs Ingress Resource
The Ingress Controller is a deployment that watches Ingress resources and configures the actual load balancer. The Ingress is just a config object — without a controller it does nothing.
yamlapiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-svc
            port:
              number: 80
  tls:
  - hosts: [myapp.example.com]
    secretName: tls-secret

NetworkPolicies

By default, all pods can talk to all pods. NetworkPolicies add firewall rules. Requires a CNI that supports them (Calico, Cilium — NOT Flannel).

The Switch That Flips to Deny
A pod starts open: it accepts traffic from anywhere. The moment any NetworkPolicy selects that pod, a switch flips — now that pod is default-deny, and only the traffic your rules explicitly allow gets through. So a policy does two things at once: it turns on the firewall for the pods it selects, and it lists what is allowed. Pods that no policy selects stay wide open.
Key Concept
An empty podSelector: {} selects ALL pods in the namespace. If a pod has any NetworkPolicy selecting it, all traffic not explicitly allowed is denied.
yaml# Allow only pods with label app=frontend to reach app=backend on port 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: backend       # this policy applies to backend pods
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend   # only from frontend pods
    - namespaceSelector:   # OR from monitoring namespace
        matchLabels:
          name: monitoring
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - ipBlock:
        cidr: 10.0.0.0/8  # allow egress to internal network only
Exam Pattern
Network policy questions often ask you to "deny all ingress and allow only specific traffic." Start by creating a deny-all policy (podSelector: {} with empty ingress: []), then add specific allow rules.
yaml# Deny all ingress for all pods in namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}   # all pods
  policyTypes:
  - Ingress

Storage

10% of exam — PersistentVolumes, PVCs, StorageClasses, and volume types. Understand the full lifecycle: admin creates PV → developer claims with PVC → pod uses PVC.

The Big Idea — Storage Is Decoupled From Pods
A pod is throw-away, but its data often is not. Kubernetes splits storage into two jobs so the app author never needs to know what disk is underneath. The admin side supplies storage: either a pre-made PersistentVolume (PV), or a StorageClass that creates PVs on demand. The developer side asks for storage with a PersistentVolumeClaim (PVC) — "I need 5Gi, read-write." Kubernetes matches the claim to a volume and binds them. The pod just names the claim. This is the same contract as RBAC: one side offers, the other requests.

Volume Types (Pod-level)

TypeLifecycleUse Case

hostPathNode lifetimeAccess node filesystem (use with care, security risk)
configMapAs long as CM existsMount config files into pod
secretAs long as secret existsMount credentials as files
persistentVolumeClaimPV lifetimeDurable storage that survives pod restarts

  volumes:
  - name: cache
    emptyDir: {}
  - name: logs
    hostPath:
      path: /var/log
      type: DirectoryOrCreate
  containers:
  - name: app
    image: myapp
    volumeMounts:
    - name: cache
      mountPath: /tmp/cache
    - name: logs
      mountPath: /var/log

PersistentVolumes (PV)

Cluster-scoped storage resource. Created by an admin. Decoupled from pods.

PersistentVolumeClaims (PVC)

A request for storage by a user/pod. K8s binds it to a matching PV automatically.

yamlapiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: manual   # must match PV storageClassName
  resources:
    requests:
      storage: 3Gi            # must be <= PV capacity
yaml# Use PVC in a Pod
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc
  containers:
  - name: app
    image: myapp
    volumeMounts:
    - name: data
      mountPath: /data

Troubleshooting

30% of exam — the biggest domain. Learn a systematic approach. Most problems have clear signals; the skill is knowing where to look.

The One Mental Model for Every Bug
Remember the control loop: every problem is "desired ≠ actual, and something blocks the fix." Your whole job is to find the blocker. Each layer tells you a different part of the story, so ask it directly:
  • Scheduling / images / mounts → kubectl describe and read the Events.
  • The app itself → kubectl logs (add --previous if it crashed).
  • The node or control plane → journalctl -u kubelet and crictl on the node.
  • Connectivity → check kubectl get endpoints and test with a temporary pod.

Troubleshooting Methodology

  1. Observe symptoms — kubectl get pods/nodes, note STATUS
  2. Describe the resource — kubectl describe, read Events section
  3. Check logs — kubectl logs, journalctl
  4. Inspect the spec — kubectl get -o yaml, check for misconfigs
  5. Test connectivity — exec into pod, curl endpoints, nslookup
  6. Fix and verify — apply change, watch rollout
